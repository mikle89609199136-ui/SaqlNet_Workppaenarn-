# Production E2E contract — CraneApp (#707)

Статус: канонический путь текущего клиента; 16 октября 2026.
Источники истины: `frontend/src/shared/crypto/{envelope,identity,signing,chatKeys,keyBackup}.ts`,
`frontend/src/services/{CryptoService,MessageService}.ts`, Go chat/user/media services.
Исторические аудиты описывают состояние на свою дату, а не этот контракт.

## Выбранный протокол

Для `private`, `group` и `self` используется **Crane envelope v2/v3**:
случайный 32-байтовый ключ на чат/эпоху, ECDH P-256 для раздачи ключа,
HKDF-SHA-256 для разделения назначений, AES-256-GCM для сообщений/медиа,
ECDSA P-256/SHA-256 для подписи отправителя. Каналы передают открытый текст;
каталожные sticker/GIF также не следует считать зашифрованными вложениями.
Signal endpoints, таблицы MLS и Rust MLS validation не делают текущий клиент
клиентом Signal/MLS. Они не участвуют в выборе протокола сообщения.
Автоматического переключения на них или на открытый текст при сбое E2E нет.

Это собственный протокол без double ratchet, forward secrecy и MLS membership
semantics. Directory публичных ключей обслуживает сервер: первый контакт
требует доверия к нему, отпечатки можно сверять отдельно. Подпись сообщения
проверяется относительно текущей и ранее сохранённых связок собеседника;
`senderVerified: false` означает неподтверждённого автора и не скрывает текст.
Свои сообщения клиент повторно не проверяет. История старых публичных связок
локальна; новое устройство может прочитать старое сообщение, но не подтвердить
подпись прежней личности, которой нет в его истории.

## Версии и байтовый контракт

Версия конверта и номер эпохи независимы. Изменение payload не сбрасывает эпоху.

| Объект                   | Запись и чтение                                                                                                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Message `v:2`            | `e2e:true, epoch, iv, data`, обычно `kid, sig`; plaintext — UTF-8 текст                                                            |
| Message `v:3`            | Те же поля; plaintext — JSON `{text,entities,voice?}`. `voice` на проводе `{d,w}`. Пишется при форматировании/voice                |
| Wrapped key `v:2`        | Base64 UTF-8 JSON `{v,iv,ct,senderId,recipientFp}`, строка API содержит `keyEpoch, senderKeyId, userId`                            |
| Media `version:2`        | `{encrypted:true,algorithm:"AES-GCM",iv,ciphertext,mimeType,sizeBytes,keyEpoch,fileName?}`                                         |
| Backup `formatVersion:1` | Зашифрованная личность, слоты мастер-ключа и отдельные зашифрованные ключи чатов/эпох. API `version` — revision для CAS, не формат |

IV — случайные 12 байт на каждое шифрование. `data`, `ct`, `ciphertext`, `sig`,
`iv` используют обычный base64. WebCrypto AES-GCM возвращает ciphertext
с 128-битным tag в конце; tag не выносится в отдельное поле.
Идентификаторы в контексте — точные строки UTF-8, разделитель — `|`.

- Message/media HKDF: IKM = chat key, salt = SHA-256(UTF-8 chatId),
  info = `craneapp/e2e/v2/msg` либо `craneapp/e2e/v2/media`, output = 256 бит.
  Epoch выбирает chat key и входит в AAD; сам HKDF info номер эпохи не содержит.
- Message v2 AAD: `chatId|epoch|senderId`; v3: `chatId|epoch|senderId|v3`.
- Signature input: `chatId|epoch|senderId|iv|data`. `kid` — подсказка,
  а не доказательство личности. Версия v3 защищена AAD, в подпись она не входит.
- Media AAD: `chatId|epoch`; ключ отделён от ключа сообщений.
- Wrap: IKM = ECDH secret, salt = SHA-256(chatId),
  info = `craneapp/e2e/v2/wrap|epoch|senderFp|recipientFp`, AES-GCM без AAD.
  Fingerprint — SHA-256 от точной строки public bundle, кодирование — в `identity.ts`.
- Backup: случайный мастер-ключ; password slot использует Argon2id с записанными
  параметрами (по умолчанию m=65536 KiB, t=3, p=1), также есть passkey/QR.
  Назначения и AAD backup задаёт `keyBackup.ts`; backup не является chat envelope.

Существующие v2/v3 читаются одновременно. Новая несовместимая версия требует
нового номера, reader-first rollout и отдельного решения о минимальной версии
клиента. Незнакомые `e2e:true` версии и `[MLS]` показываются как `legacy`,
не пробуются другими алгоритмами. Current envelope с ошибкой AEAD-аутентификации возвращает `keyUnavailable`
вместо plaintext. Старые файлы version 1 не расшифровываются.

## Эпохи, устройства и восстановление

1. Личность аккаунта общая для устройств и приходит из зашифрованной копии.
   Чистое устройство просит открыть её паролем, passkey или QR; молчаливой
   генерации новой личности при наличии копии нет.
2. ChatKeyManager ищет эпоху локально, затем свою текущую wrapped row на сервере,
   затем в копии. Серверная раздача хранит текущие строки, архив эпох — устройство
   и backup. Без сохранённого ключа ciphertext восстановить невозможно.
3. Изменение состава поднимает `rotationNeeded`. Любой текущий участник может
   создать новый случайный ключ эпохи N+1 для текущего состава. Сервер принимает
   запись атомарно; конкурентный проигравший принимает победивший ключ. Старый
   ключ новичку при ожидающей ротации не раздаётся. Старые эпохи не удаляются.
4. При смене recipient fingerprint текущий ключ перезаворачивается (`heal`);
   это не повод отдавать новичку архив. При сбросе личности без возможности
   открыть backup прежняя история остаётся недоступной. Новая эпоха продолжает
   серверную нумерацию, а не начинает её с 1.
5. Без realtime epoch подхватывается по envelope при чтении (`forEpoch`).
   При отправке локальная эпоха периодически сверяется с сервером (30 секунд).
   После reconnect список чатов инвалидируется, активный чат загружает последнюю
   страницу и расшифровывает сообщения, затем повторяется клиентский outbox.
   Повторная синхронизация объединяет сообщения по ID и обновляет уже загруженные
   сообщения (включая правки и заглушки расшифровки), сохраняя старые страницы.
   Более свежая realtime-правка не заменяется старой версией из HTTP-ответа.
   Изменения реакций, receipts, закреплений и удаления, полученные во время
   запроса, повторно применяются поверх snapshot; сравнение `updatedAt`
   не используется как версия этих независимых полей.

Ограничения восстановления: reconnect сейчас загружает **одну страницу (50)**,
а не весь произвольный разрыв. Пропущенные изменения старых страниц требуют
перезапроса истории; realtime не является журналом с replay cursor. Outbox не
даёт серверной идемпотентности отправки при потере HTTP-ответа: повтор может
создать дубликат с другим ID. Эти ограничения нельзя трактовать как гарантию
полного offline sync. Несохранённые в backup ключи потерянного устройства
не восстанавливаются. `beforeJoin` — вывод клиента по самой ранней известной
эпохе; это не серверное доказательство даты вступления.

## Операции и границы metadata

- Reply шифрует новый текст текущей эпохой; `replyTo` остаётся открытым ID.
- Edit шифрует текст заново текущей эпохой, заменяет content и форматирование.
  Для чтения правки нужен ключ новой эпохи, даже если исходное сообщение старое.
- Forward читает plaintext на устройстве, шифрует его ключом целевого чата и
  подписывает как пересылающий. Медиа расшифровывается и загружается заново.
  Сервер проверяет `forwardedFrom` и устанавливает origin metadata.
  Пересылка `undecryptable` запрещена.
- Текст, entities и voice metadata находятся внутри message ciphertext.
  Тип, ID чата/автора, время, reply/forward linkage, размеры, MIME и media URL
  видны серверу; они не все защищены подписью/AAD. Нельзя заявлять целостность
  reply/forward linkage на основании подписи текста.
- Для media сервер проверяет принадлежность загрузки отправителю, адрес своего
  media API и берёт encryption metadata из записи загрузки. Клиентское
  `mediaEncryption` может быть заменено: это предусмотренный контракт.
- Content конверта в БД, HTTP history/response и realtime должен совпадать
  строка-в-строку: без HTML escaping, изменения base64, epoch, kid, sig или v.
  Сериализация внешнего JSON допустима; сравнивается декодированная строка content.
- Обычная Go отправка коммитит сообщения и непосредственно делает broadcast.
  Она не пишет событие в `messages.outbox`. Отдельный OutboxRelay оборачивает
  сохранённый payload внешним event envelope; вложенный content и поля metadata
  сохраняются. Тест relay не доказывает durable delivery обычной отправки.

## Миграция, rollout и rollback

- Legacy wrapped keys совместимого v2 и локальные эпохи импортируются в backup
  при его настройке; миграция сохраняет ключи чатов и перезаворачивает свою строку
  для backup identity. Сначала завершить backup upload, затем проверять чистое
  устройство. Нельзя удалять локальное хранилище до успешной проверки.
- Предыдущие self-contained envelopes и `[MLS]` не конвертируются сервером.
  Клиент показывает заглушку `legacy`; ciphertext сохраняется для аудита.
  Сбрасывать ключи, массово перешифровывать историю или экспортировать plaintext
  на сервер в рамках миграции запрещено.
- Signal/MLS rows сохраняются как неактивные данные. Не удалять таблицы и не
  переиспользовать их epoch для envelope. Настоящий переход на Signal/MLS —
  отдельная миграция с capability negotiation и проверкой истории.
- Выпускать backend с opaque-content поддержкой и атомарной ротацией прежде
  клиента. Проверить private/group/self и новый браузер, затем расширять rollout.
  Клиенты без v3 не могут читать rich/voice сообщения; минимально допустимый
  rollback клиента обязан читать v2/v3 и backup v1.
- При регрессии остановить расширение rollout и вернуть последний совместимый
  клиент/backend. Сохранить ciphertext, текущие epoch, wrapped rows и backup
  revision. Не понижать epoch, не восстанавливать старый ключ поверх нового,
  не включать plaintext fallback. Schema rollback с удалением crypto данных
  недопустим. Если совместимого релиза нет — приостановить отправку до исправления.

## Наблюдаемость и проверка выпуска

Доступные клиенту сигналы: `undecryptable` (`legacy`, `keyUnavailable`, `beforeJoin`),
`senderVerified:false`, состояния backup (`needsSetup`, `locked`, `ready`, `error`,
`unavailable`) и chat encryption, отказы decryptMedia. Сбой криптооперации
попадает в `console.warn`; отсутствие ключа может вернуть заглушку без лога.
Сервер видит конфликты epoch/rotation, HTTP ошибки backup/key/media и ошибки relay,
но не знает, успешно ли получатель расшифровал сообщение. Централизованной метрики
ошибок клиентской расшифровки сейчас нет. При сборе QA-диагностики фиксировать
версию клиента/конверта, категорию ошибки, этап восстановления и наличие эпохи;
не собирать plaintext, пароль, ключи, backup blobs или полные envelopes.

Release gate: необъяснимые `keyUnavailable` после unlock/reconnect, новые массовые
`senderVerified:false`, потеря старых эпох либо изменение wire content останавливают
rollout до воспроизведения и исправления. `legacy` и ожидаемое отсутствие истории
до вступления учитываются отдельно от регрессии.

Автоматизированная проверка (из корня):

```sh
npm --prefix frontend test -- src/services/e2eProtocol.node.test.ts src/services/mediaProtocolCompatibility.node.test.ts src/shared/crypto/ src/services/MessageService.node.test.ts src/realtime/resyncAfterReconnect.node.test.ts src/entities/message/model/outboxSender.node.test.ts src/features/forward-messages/model/useForwardSend.test.tsx src/realtime/rotateOnMembershipChange.test.tsx
cd backend-v2
go test -tags integration ./internal/chat ./internal/user ./internal/media
```

Go integration требует Docker/Postgres testcontainers. `e2eProtocol.node.test.ts`
использует настоящие CryptoService, MessageService, backup/key managers и WebCrypto,
подменяя удалённый транспорт. Он проверяет чистое устройство, v2/v3, media старой
эпохи, reply/edit/forward, reconnect с пропуском ключа и отказ при повреждении.
Go `TestE2EProtocolOpaqueTransport` проверяет HTTP → настоящий Postgres → history →
realtime для v2/v3; `TestE2EOutboxPreservesCiphertextAndMetadata` проверяет relay
отдельно. Это integration coverage, а не прогон двух настоящих браузеров.

`protocolCompatibility.node.test.ts` отдельно читает **фиксированные** v2/v3
конверты, подписи, media и wrapped key из `e2eProtocolVectors.ts`, а также
сравнивает запись с заранее известными байтами при фиксированном тестовом IV.
`mediaProtocolCompatibility.node.test.ts` проверяет публичные `CryptoService.encryptMedia/decryptMedia`:
целиком фиксируются `encrypted`, `version`, `algorithm`, `keyEpoch`, MIME, размер,
IV и ciphertext; проверка не ограничивается AES-байтами.
Векторы созданы отдельным генератором `scripts/generate-e2e-protocol-vectors.cjs`
на Node crypto без импорта модулей приложения. Ключи и IV в них — публичные
тестовые данные. Тесты не запускают генератор: изменение HKDF/AAD/сериализации
под прежним номером версии должно ломать проверку совместимости. Нельзя
перегенерировать векторы для исправления такого падения; новая версия протокола
должна добавлять новые векторы, сохраняя проверку чтения прежних.

Перед production дополнительно проверить в двух отдельных профилях браузера:
переписку и файл, отключение сети у получателя, смену состава группы и новые
сообщения, возврат сети, повторный reconnect, reply/edit/forward в другой чат,
затем новый профиль с unlock backup. Старый участник читает свою историю,
новый участник не получает ключ до вступления, удалённый не читает новую эпоху;
устройство без unlock не отправляет plaintext. Проверить также разрыв >50 сообщений
как известное ограничение, без заявления о полном восстановлении такого разрыва.
