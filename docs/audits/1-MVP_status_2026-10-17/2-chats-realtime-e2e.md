Комментарий в задаче устарел: «пять попыток раз в секунду» и «после восстановления ресинхронизации нет» больше не соответствуют коду (`WebSocketClient.ts:203-225`, `resyncAfterReconnect.ts`). Стоит добавить сценарии «второе устройство открывает копию» и «два устройства одновременно»: они заявлены в #739, но в репозиторий не попали.
- **#425** (crypto недоступен → ложный 401) — актуальна без изменений (`authctx.go:43-50`). Для надёжности MVP это блокер: ложный 401 разлогинивает пользователей (`AuthGuard.tsx:12-24`). Метки `mvp-go` нет; предлагаю её добавить.

## Пробелы без задачи

- Свои сообщения, правки и прочтения не доходят до других своих устройств и вкладок, включая «Избранное» — бэкенд (`service.go:2410`, `:2538`, `receipts.go:221`) и немного фронта; **M**.
- Восстановление после reconnect не обновляет кешированные неактивные чаты и закреплённые; из-за этого «залипает» счётчик непрочитанных — фронт (`resyncAfterReconnect.ts:25-32`); **S**.
- Восстановление после reconnect не применяет пропущенные удаления (в пределах свежей страницы нужно убирать отсутствующие ID) — фронт (`threadCacheActions.ts:134-145`); **S**.
- Нет догонки разрыва больше 50 сообщений (курсор `since` или постраничная догрузка до известного ID) — бэкенд и фронт; **M**.
- Нет идемпотентности отправки (`clientMessageId` + уникальный индекс), из-за чего при потере ответа появляются дубликаты — бэкенд и фронт; **M**.
- Нет клиентского сторожевого таймера heartbeat для полуоткрытого сокета — фронт (`WebSocketClient.ts`); **S**.
- При заполненном буфере сервер молча теряет события. Лучше закрывать такое соединение, чтобы клиент переподключился и догнал пропущенное — бэкенд (`ws.go:719-727`); **S**.
- При отозванной или истёкшей сессии WS переподключается бесконечно без проверки сессии — фронт; **S**.
- Нет `ErrorBoundary`/`errorElement`: любая ошибка рендера или загрузчика, включая перезагрузку без сети, роняет всё приложение — фронт (`router.tsx`); **S**.
- Outbox теряется при перезагрузке без предупреждения — фронт (`outboxStore.ts:39-48`): **S**, если только предупреждать через `beforeunload`; **M**, если хранить очередь зашифрованной.
- Автоповтор outbox только при reconnect сокета, не при возвращении сети и не по таймеру — фронт (`outboxSender.ts:176-203`); **S**.
- Нет ограничения частоты запросов к `/api/v2/encryption/backup` (в `backend-v2/internal/platform/ratelimit` и `docs/security/rate-limiting.md` упоминаний нет) — бэкенд; **S**. Подбор облачного пароля всё равно идёт офлайн по выданному слоту; ограничение лишь снижает массовый сбор.

## Риски и зависимости

- **Масштабирование чата.** Хаб WS живёт в памяти процесса. `new_message` и остальные события рассылаются только своим соединениям (`ws.go:669-727`); между репликами передаются только отзывы и блокировки через Postgres NOTIFY (`ws_revocation.go:14`, `block_change_relay.go:19`). В проде один процесс `chat` (`supervisord.conf:75-76`). Вторая реплика сломает доставку.
- **Модель угроз E2E.** Протокол собственный, без forward secrecy и double ratchet. Каталог публичных ключей обслуживает сервер, первый контакт требует доверия к нему (`docs/crypto/production-e2e.md:19-26`). Мастер-ключ копии лежит в IndexedDB в открытом виде (`keyBackupManager.ts:116`, `:130`): XSS или доступ к профилю браузера открывают всю историю. Серверу видны метаданные: тип, связи reply/forward, имя файла, MIME, размер (`production-e2e.md:110-113`).
- **Ложные выходы при сбое crypto-сервиса** (#425) — массовый выход пользователей при частичной аварии.
- **Нагрузка от проверки отзыва**: запрос к БД или Redis на каждое входящее WS-сообщение и на каждый heartbeat (`ws.go:306`, `:609`, `ws_revocation.go:47-71`).
- **Нет автоматических браузерных тестов** (#277) нескольких устройств, копии ключей и обрыва. Регрессии в самых рискованных сценариях ловятся только руками; перед выпуском нужен ручной прогон по `docs/crypto/production-e2e.md:194-200`.
- **Зависимость #852 → протокол**: задачу нельзя выполнять буквально («сессии Signal»), сначала нужно согласовать её с выбранным протоколом.
- **Список чатов без пагинации** — один тяжёлый агрегирующий запрос на каждое обновление списка (`service.go:451-546`), а обновление вызывает каждое `new_message` (`invalidationMap.ts:28-29`); связано с #131.
