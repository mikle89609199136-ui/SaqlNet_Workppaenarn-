# Аудит криптографического слоя

**Дата:** 25 августа 2026
**Ветка:** `master`, коммит `be44a9e`
**Что проверено:** генерация и хранение ключей, обмен публичными ключами, шифрование и расшифровка личных сообщений, групповые чаты, медиафайлы, серверные схемы хранения ключей.
**Метод:** чтение исходников фронтенда и `backend-v2`, сверка с миграциями БД. Вживую воспроизводился только дефект расшифровки — по логам дев-сервера.

---

## Резюме

Личные сообщения защищены настоящим сквозным шифрованием. Групповые — нет: вместо шифрования применяется base64. Схема ключей рассчитана на одно устройство и один ключ навсегда, поэтому вход со второго устройства необратимо ломает доступ к переписке.

Отдельно: на сервере готова инфраструктура для полноценной схемы — ключи по устройствам, ротация, постквантовые поля, MLS. Фронтенд не использует ничего из этого.

| Область | Реальная защита |
|---|---|
| Личные сообщения, текст | ECDH P-256 + AES-GCM — сквозное шифрование |
| Личные сообщения, медиа | ECDH P-256 + AES-GCM — сквозное шифрование |
| Групповые сообщения, текст | **отсутствует** — base64 |
| Групповые медиа | AES-GCM, но ключ выводим сервером |
| Ротация ключей | отсутствует |
| Работа с двух устройств | ломает доступ к истории |

---

## Как устроено сейчас

Одна пара ECDH P-256 на аккаунт.

1. При входе `CryptoService.init()` читает `localStorage` и берёт идентификатор аккаунта.
2. `doInit` открывает IndexedDB `craneapp_crypto` и ищет запись `signal_keypair:{accountId}`.
3. Если записи нет — `generateAndStoreKeys` создаёт пару, сохраняет в JWK и публикует публичный ключ.
4. Публикация — `POST /api/v2/auth/public-key`, таблица `auth.public_keys` с `PRIMARY KEY (user_id)`.
5. При открытии чата сервер отдаёт `peerPublicKey` в составе чата.
6. Отправка: `ECDH(мой приватный, публичный собеседника)` → AES-GCM.
7. Получение: тот же вывод общего секрета в обратную сторону.

Для личных чатов это корректная реализация. Проблемы начинаются за её пределами.

## Находки

### 1. Групповые сообщения не шифруются

**Где:** `frontend/src/services/CryptoService.ts:451`

```js
// Mock MLS encryption based on legacy script
return `[MLS]${btoa(encodeURIComponent(content))}`;
```

`btoa` — кодирование base64, а не шифрование. Расшифровка симметрична: `atob`. Содержимое любого группового чата восстанавливается из базы или из трафика одной строкой.

При этом `syncGroupState` запрашивает MLS-состояние по `GET /chats/{id}/mls-state` и сохраняет его в IndexedDB — в шифровании оно не участвует. В интерфейсе групповой чат неотличим от защищённого.

Комментарий в коде честно называет это заглушкой, то есть работа не выдаётся за законченную. Но пока она не закончена, для групповых чатов обещание сквозного шифрования не выполняется.

### 2. Ключ групповых медиафайлов выводим сервером

**Где:** `frontend/src/services/CryptoService.ts:554`

```js
const material = JSON.stringify({ purpose: 'craneapp-media-v1', chatId, state });
const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(material));
```

`state` приходит с сервера. Значит сервер располагает всеми входными данными, чтобы получить тот же AES-ключ и расшифровать вложения.

Криптография настоящая — AES-GCM, — но это шифрование при передаче, а не сквозное. Для личных чатов медиа выводятся через `deriveDMKey` с реальным ECDH, где сервер бессилен. Разница между личными и групповыми чатами принципиальная и нигде не отражена.

### 3. Вход со второго устройства уничтожает доступ к переписке

**Где:** `backend-v2/internal/auth/service.go:190`

```sql
INSERT INTO auth.public_keys (user_id, public_key, updated_at)
VALUES ($1, $2, NOW())
ON CONFLICT (user_id) DO UPDATE SET public_key = EXCLUDED.public_key, updated_at = NOW()
```

`PRIMARY KEY (user_id)` — один ключ на пользователя. Приватный ключ живёт в IndexedDB конкретного браузера и никуда не синхронизируется.

На новом устройстве `doInit` не находит ключей, генерирует новую пару и затирает публичный ключ на сервере. Последствия:

- на новом устройстве не читается ничего из прежней переписки;
- собеседники перестают читать ваши прежние сообщения — те ссылаются на затёртый ключ;
- на старом устройстве всё продолжает работать, пока не отправлено что-то новое.

Это не незавершённая функция, а архитектурное ограничение: мультиустройство в текущей схеме невозможно.

### 4. Расхождение имён в E2E-payload

**Где:** `CryptoService.ts:299` и `CryptoService.ts:352`. Заведено как **#234**.

```ts
// шифрование пишет
recipientPubKeyB64: recipientPubKeyB64,

// расшифровка читает
: payload.recipientPublicKey || senderPubKeyB64;
```

Поле `recipientPublicKey` в payload не появляется никогда, поэтому в ветке для собственных сообщений всегда срабатывает запасной вариант — текущий ключ собеседника с сервера.

Ветка выбирается в `MessageService.ts:275` по автору сообщения:

| Сообщение | Флаг | Ключ | Результат |
|---|---|---|---|
| чужое | `preferEmbeddedSenderKey: true` | `payload.senderPublicKey` — есть | читается |
| своё | `preferEmbeddedSenderKey: false` | `payload.recipientPublicKey` — нет | запасной вариант |

Пока собеседник ключ не менял, запасной вариант совпадает с нужным и дефект невидим. После смены ключа собственные отправленные сообщения перестают читаться, хотя нужный ключ лежит в том же payload под именем `recipientPubKeyB64`.

Замысел был верным — ключ получателя вшивается в сообщение именно для того, чтобы оно пережило ротацию. Механизм есть, данные сохраняются, читают их не по тому имени.

**Сопутствующее:** текст ошибки вводит в заблуждение. Условие `keyMismatch` (`CryptoService.ts:382`) сравнивает мой ключ с `payloadRecipientKeyFp`. Для входящего сообщения это мой ключ, сравнение осмысленно. Для исходящего — ключ собеседника, который с моим не совпадёт никогда, поэтому на своих сообщениях всегда показывается «Ключ собеседника изменился» независимо от настоящей причины.

### 5. Провал публикации ключа не повторяется

**Где:** `CryptoService.ts:110`

```js
if (!this.publicKeyUploaded) {
  await this.uploadPublicKey();   // внутри try/catch, ошибка проглатывается
  this.publicKeyUploaded = true;  // ставится в любом случае
}
```

Если запрос упал, флаг всё равно выставляется, и повторной попытки не будет до перезагрузки вкладки. Собеседники не получат ключ, и все сообщения за эту сессию окажутся для них нечитаемыми. Ошибка видна только в консоли.

Похоже, это механика **#192**, где симптом описан как «после перезагрузки IndexedDB инициализируется и ошибка пропадает».

### 6. Ненадёжный идентификатор аккаунта

**Где:** `CryptoService.ts:119`

```js
return user?.id || user?.username || null;
```

Если `id` отсутствует, ключи сохранятся под `signal_keypair:{username}`. Смена username приведёт к потере доступа к ключам без какого-либо сообщения.

### 7. Ротации ключей нет

`generateAndStoreKeys` вызывается ровно в одном месте — когда в IndexedDB пусто. Метода для перевыпуска не существует.

При компрометации ключа единственный путь — вручную очистить хранилище, потеряв всю историю. При этом на сервере ротация предусмотрена, см. следующий раздел.

### 8. Типы не защищают в самом уязвимом месте

Два ослабления типизации, каждое уже стоило дефекта.

`CryptoService.ts:344`:

```ts
const payload: IE2EPayload = JSON.parse(payloadStr);
```

`JSON.parse` возвращает `any`. Приведение ничего не проверяет: отсутствующее поле объявлено необязательным, лишнее не проверяется вовсе. Именно это пропустило находку №4.

`frontend/src/types/chat.types.ts:42`:

```ts
export interface IChatContext {
  type: TChatType;
  peerPublicKey: string | null;
  [key: string]: unknown;
}
```

Индексная сигнатура разрешает любое поле. В `getMediaKey` благодаря ей компилируются обращения к `chatContext.recipientPublicKey`, `.senderPublicKey`, `.publicKey`, тогда как `getChatContext` возвращает только `type` и `peerPublicKey`. Три из четырёх запасных вариантов недостижимы, и компилятор об этом не сообщит.

## Что готово на сервере и не используется

`backend-v2/internal/user/encryption.go`, миграция `backend-v2/migrations/0009_crypto.sql`.

| Возможность | На сервере | Использует фронт |
|---|---|---|
| `POST /api/v2/encryption/keys` с `keyId` и `pqPublicKey` | есть | нет |
| `GET /api/v2/encryption/keys/{userId}` | есть | нет |
| `chat-keys` — сессионный ключ, обёрнутый для каждого участника, с `key_epoch` | есть | нет |
| `POST /api/v2/encryption/rotate-key/{chatId}`, лимит 10 ротаций в час | есть | нет |
| Типы `SignalIdentityKey`, `SignalSignedPreKey`, `SignalOneTimePreKey`, `SignalPreKeyBundle` | объявлены | нет |
| Постквантовые поля `pq_public_key`, `pq_ciphertext` | в схеме | нет |
| MLS: `user_mls_keypackages`, `group_mls_state`, `group_mls_commits` | таблицы есть | только чтение состояния |

Фронтенд публикует ключ единственным примитивным маршрутом `/auth/public-key`. Имя записи в IndexedDB — `signal_keypair` — отсылает к Signal-протоколу, реализации которого в коде нет.

**Схем хранения ключей три:**

- `auth.public_keys` — миграция `0001_auth.sql`, используется;
- `crypto.user_public_keys` — миграция `0009_crypto.sql`, не используется;
- `user_public_keys` — `database/database.js`, наследие Node-гейтвея.

Какая считается основной, по коду определить нельзя.

## Что предстоит решить

Правка по #234 — одна строка, и она закрывает конкретный симптом. Но сама по себе она ничего не меняет в устройстве схемы: ключ остаётся один, устройство одно, ротации нет, групповые чаты не защищены.

Два направления, между которыми предстоит выбрать:

**Целевая схема ключей.** Переход на `/api/v2/encryption/keys` с `keyId`, ключи по устройствам вместо одного на аккаунт, ротация с сохранением доступа к истории. Серверная часть готова, работа преимущественно фронтовая.

**Настоящее шифрование групп.** Замена заглушки на MLS. Таблицы `user_mls_keypackages`, `group_mls_state` и `group_mls_commits` существуют, но объём работы здесь значительно больше и затрагивает обе стороны.

До принятия решения имеет смысл завести задачи на находки 1, 3 и 5 — они наиболее весомые и сейчас нигде не зафиксированы.
