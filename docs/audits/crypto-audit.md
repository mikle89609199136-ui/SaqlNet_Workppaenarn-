# Аудит криптографического слоя: статус документа

**Первичный аудит:** 25 августа 2026, commit `be44a9e`<br>
**Актуализировано:** 18 сентября 2026, commit `d93a9ab`

Первоначальная версия этого файла описывала старую демонстрационную схему: статический ECDH для личных сообщений и base64-заглушку `[MLS]` для групп. Эта схема больше не является текущей.

Подробный актуальный разбор находится в [`crypto-e2e-review-2026-08-27.md`](./crypto-e2e-review-2026-08-27.md). Этот файл оставлен как короткая карта изменений, чтобы старые выводы не воспринимались как состояние продукта.

## Что изменилось после первичного аудита

| Старая находка | Текущий статус |
|---|---|
| Групповые сообщения хранились в base64 | **Исправлено.** Личные и групповые чаты используют общий симметричный ключ чата, завёрнутый отдельно для участников. |
| Сервер мог прочитать ключ группового медиа из MLS-state | **Исправлено.** Текст и медиа шифруются клиентом ключом чата разных назначений. |
| Сообщения не имели криптографической подписи | **Исправлено.** Envelope v2 подписывается ECDSA P-256; chat/epoch/sender/ciphertext связаны подписью и AEAD. |
| Сырой ECDH использовался прямо как AES-key | **Исправлено.** Используется HKDF-SHA-256 с контекстом чата и назначением `msg`, `media`, `wrap`. |
| Приватные ключи сохранялись извлекаемым JWK | **Исправлено.** Приватные ECDH/ECDSA `CryptoKey` создаются с `extractable: false` и хранятся в IndexedDB. |
| Публикация ключа могла считаться успешной после ошибки | **Исправлено.** Публикация повторяется при следующей инициализации. |
| Payload читал другое имя recipient key | **Неактуально.** Старый payload заменён envelope v2. |
| Серверные `chat-keys`/rotation не использовались | **Исправлено.** Их использует `ChatKeyManager`; при смене состава владелец инициирует новую эпоху. |
| Signal routes не были зарегистрированы | **Исправлено на backend.** Routes зарегистрированы, но текущий frontend использует собственный envelope v2, а не Signal double ratchet. |

## Что всё ещё не закрыто

- Нет forward secrecy внутри эпохи: один chat key действует до ротации состава.
- Нет полноценной multi-device identity: на backend остаётся одна текущая связка ключей пользователя.
- Новое устройство не может самостоятельно восстановить старые локальные ключи/историю.
- Доверие при первом контакте остаётся у сервера. UI сообщает о последующей смене ключа, но не показывает полноценный safety-code flow для внешней сверки.
- Одновременное создание/перезапись ключей одной эпохи не транзакционно и требует интеграционных race-тестов.
- Signal/MLS infrastructure существует параллельно текущему протоколу и увеличивает число конкурирующих схем.

## Текущая оценка

Текущая реализация — реальное клиентское шифрование текста и медиа, существенно сильнее старой заглушки. Но без внешней проверки личности, forward secrecy и multi-device protocol её нельзя считать завершённым production-grade аналогом Signal/Telegram Secret Chats.

Перед MVP нужны как минимум:

1. Зафиксированная модель угроз и название протокола без заявления о Signal/MLS, если они фактически не используются.
2. E2E-тесты двух браузеров: private/group, media, rotation, reconnect, новый участник, удалённый участник и смена устройства.
3. Safety code/fingerprint UI с внешней сверкой.
4. Решение по multi-device и восстановлению истории.
5. Устранение параллельных legacy/Signal/MLS контрактов либо ясное документирование их роли.
