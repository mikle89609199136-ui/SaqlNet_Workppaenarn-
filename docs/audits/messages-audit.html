Дефекты

Каждый проверен по коду. Указано место, поведение и почему это не поймали компилятор или тесты.

ломает

Открепление не убирает сообщение из кеша

MessageService.ts:455 
// сигнатура принимает идентификатор сообщения
removePinnedMessageFromCache(messageId: string) {
  ... messages.filter((message) => message.id !== messageId)
}

// а вызывают её с идентификатором чата
async unpinMessage(chatId: string, messageId: string) {
  await this.apiClient.delete(...);
  this.removePinnedMessageFromCache(chatId);
}

Идентификатор чата никогда не совпадёт с идентификатором сообщения, поэтому фильтр не удаляет ничего. На сервере сообщение откреплено, в кеше остаётся — при повторном открытии чата оно снова в закреплённых.

Почему не поймали: оба параметра — string. Для TypeScript вызов корректен. Тестов на сервис, кроме четырёх на пересылку, нет.

ломает

Первое сообщение в списке не помечается прочитанным

store/chat.ts:102 
const messageIndex = messages.findIndex((m) => m.id === messageId);

if (!messageIndex) return;  // findIndex вернул 0 — это валидный индекс

findIndex возвращает -1, когда не нашёл, и 0 для первого элемента. Проверка !messageIndex отсекает ноль и пропускает минус единицу — то есть ведёт себя ровно наоборот: первое сообщение молча пропускается, а ненайденное записывается в messages[-1].

Правильная проверка: if (messageIndex === -1) return;

ломает

Реакции исчезают после выхода из чата

useMessageActions.ts:123

Ответ сервера кладётся в стор через updateMessage, но не в кеш сервиса. А getMessages при повторном открытии чата отдаёт именно кеш — с прежними реакциями. Метод updateMessageInCache в проекте есть и вызывается ровно в одном месте: при редактировании сообщения.

Корень: два независимых хранилища одних и тех же данных — Map внутри сервиса и стор Zustand. Синхронизировать их вручную приходится в каждом обработчике, и в большинстве об этом забыли.

ломает

Реакция собеседника не появляется без перезагрузки

consts/wsEvents.ts:29

Сервер отправляет reaction_updated (service.go:1746). На фронте событие объявлено в константах и типизировано в wsEvents.types.ts — но ни один компонент на него не подписан. Поиск по src/ даёт только эти два объявления.

Итого: реакции в реальном времени не работают ни в одну сторону — свои теряются из-за кеша, чужие не приходят вовсе.

вхолостую

Отметка о прочтении никуда не выводится

store/chat.ts:105 · message.types.ts:30 
const readMessage = { ...message, isRead: true, status: 'read' };

Полей isRead и status нет в интерфейсе IMessageDto, и ни один компонент их не читает. Галочек прочтения в интерфейсе тоже нет — поиск по MessageBubble и MessagesList пуст.

Что это значит: цепочка «запрос на сервер → событие → обновление стора» отрабатывает полностью и заканчивается ничем. Пользователь не может узнать, прочитано ли его сообщение.

подвисает

Подгрузка истории ломается навсегда после ошибки или смены чата

ChatThreadPage.tsx:139 
setIsLoadingMore(true);
const older = await getMessages({ chatId, offset: nextOffset });

if (chatIdRef.current !== requestChatId) {
  return;  // setIsLoadingMore(false) не вызовется
}

Ранний выход не сбрасывает флаг, а try/catch вокруг запроса нет вообще. Достаточно переключить чат во время загрузки или поймать сетевую ошибку — и isLoadingMore остаётся true, а вместе с ним прокрутка вверх перестаёт что-либо подгружать до перемонтирования страницы.

При латентности стенда 1,2–1,9 с окно для такого переключения — больше секунды на каждую подгрузку.

Реакция не ставится молча

useMessageActions.ts:118 
if (message.reactions.find((r) => r.myReaction) && !currentUser?.isPremium)
  return;  // ни тоста, ни блокировки кнопки

Пользователь без премиума, уже поставивший одну реакцию, нажимает на эмодзи — не происходит ничего. Ни подсказки, ни визуального отличия недоступных кнопок.

Смежное: ограничение живёт только на клиенте. Серверная часть этого правила — задача #145 и её подзадачи, там же три PR в общей ветке.

подвисает

Кеш закреплённых не обновляется при закреплении

MessageService.ts:419 · 444

listPins возвращает кеш, если он есть, без всякой проверки свежести. При этом pinMessage кеш не трогает — новое закреплённое появится в списке только потому, что ChatThreadPage отдельно вызывает addPinnedMessageToCache в обработчике WebSocket-события. Прямой путь «нажал закрепить → увидел в списке» держится на этом обходном пути.

Рядом: updatePinnedMessageInCache не вызывается нигде — мёртвый код.

вхолостую

Отправка без оптимистичного отображения

useComposerSendMessage.ts:85

Сообщение появляется в ленте только после ответа сервера — на стенде это 1,2–1,9 секунды тишины после нажатия. Статусов «отправляется» и «не отправлено» нет, повторной отправки при ошибке нет: текст остаётся в поле ввода, а ошибка уходит в общий setError.

Справедливости ради: сама обработка сделана аккуратно — try/catch/finally, защита от двойной отправки, дедупликация через appendUniqueMessage. Не хватает именно обратной связи.

долг

Кеш сообщений живёт вечно

MessageService.ts:51 
const cached = this.messages.get(chatId);
if (cached && offset === 0) return cached;  // без срока и без инвалидации

Единственный способ увидеть свежую историю — перезагрузить вкладку. Именно этот механизм породил задачу #174: пересылка добавляла в пустой кеш одну запись, и та принималась за всю историю чата. Тогда починили симптом; сам механизм остался.

Кандидат на замену: TanStack Query — кеш, инвалидация и дедупликация запросов вместо ручного Map. Это обсуждалось и вынесено в #225.

долг

Расхождение имён в E2E-payload

CryptoService.ts:299 · 352 
encryptDM:  recipientPubKeyB64: recipientPubKeyB64
decryptDM:  payload.recipientPublicKey || senderPubKeyB64

Пишется одно поле, читается другое, поэтому в ветке расшифровки всегда срабатывает запасной вариант — текущий ключ собеседника с сервера. Пока собеседник ключ не менял, значения совпадают и ошибка невидима. После смены ключа собственные отправленные сообщения перестают читаться, хотя нужный ключ лежит в том же payload.

Почему не поймали: JSON.parse возвращает any, результат приводится к IE2EPayload, где поле объявлено необязательным. Лишнее поле не проверяется, отсутствующее — тоже. Относится к задаче #192.

Чего нет

Первые две позиции — готовые серверные маршруты без единой строки на фронте. Остальное заведено в задачи, но не начато.

Порядок работ

Сверху — то, что дёшево починить и что видно пользователю сразу.

  1. Три однострочника

    Аргумент в unpinMessage, проверка индекса в markAsRead, имя поля в CryptoService. Каждая правка — одна строка, каждая закрывает видимый дефект.

  2. Реакции целиком

    Подписка на reaction_updated плюс запись в кеш сервиса. Без обоих кусков реакции не работают ни для отправителя, ни для получателя.

  3. Флаг загрузки и обработка ошибок в подгрузке

    try/finally вокруг запроса в loadMoreMessages. Одна из тех поломок, что не воспроизводятся на быстрой сети и стабильны на медленной.

  4. Галочки прочтения

    Добавить isRead и status в IMessageDto и вывести в MessageBubble. Вся серверная часть уже работает — не хватает последнего шага.

  5. Единое хранилище истории

    Задача #225. Пока данные лежат в двух местах, каждый новый обработчик будет забывать про одно из них — три дефекта выше именно об этом.

  6. Поиск и избранное

    Серверная часть готова, работа чисто фронтовая. Хорошие кандидаты в самостоятельные задачи для второго разработчика.

Проверено по коду ветки master на коммите be44a9e. Каждый дефект подтверждён чтением исходников; вживую воспроизводился только дефект расшифровки — по логам дев-сервера.

Звонки, авторизация и групповые права в этот аудит не входили.
