# Модель доступа к скачиванию media

Решение по #615 (MEDIA-D002). Фиксирует целевую модель для
`GET`/`HEAD /api/v2/media/{uploadId}` и заменяет временное поведение из #202.

Модель доступа реализована в #986 / PR #995: маршруты защищены cookie-сессией
и ACL, связи и факт прикрепления добавлены миграцией `0044_media_access.sql`.
Физическое удаление объектов и очистка сирот остаются в открытой #987.
#615 — документационная задача: она фиксирует модель и границы реализации.
Закрытие #615 не означает выполнения очистки из #987.

## Исходное состояние до #986

`GET` и `HEAD` отдавали объект любому, кто знал `uploadId`: на маршруте не было
проверки подписи токена и отзыва сессии. В контракте у операций отсутствовало
`security`, то есть поведение было задокументировано как публичное.

В схеме уже были `media.uploads.uploader_id` с FK на `auth.users`, каскадом
и индексом. Связей загрузки с сообщением и чатом не было: ссылка на файл
лежала в `messages.messages.metadata` (jsonb) без FK и индекса.

Поле `purpose` присутствовало в контракте загрузки и читалось хендлером, но
в базу не записывалось.

После #973 тот же маршрут принимает также `media.stickers.id` и
`media.sticker_packs.id` для иконки пака. Эти объекты хранят `bucket/object_key`
в собственных таблицах и не имеют строки в `media.uploads`. Имя параметра
`uploadId` в контракте сохраняется, но фактически это идентификатор медиа.

## Классы доступа

Назначение, заявленное при загрузке, не даёт прав. Права даёт только
фактическая привязка.

| Основание доступа | Кто получает файл |
|---|---|
| Действующая связь с сообщением | участники чата этого сообщения |
| Действующая связь с аватаром профиля | любой авторизованный |
| Действующая связь с аватаром группы | участники этой группы |
| Действующая связь с публикацией в библиотеке GIF | любой авторизованный |
| Управляемый стикер существующего пака | любой авторизованный |
| Управляемая иконка существующего пака | любой авторизованный |
| Связей нет и прикрепления никогда не было | только загрузивший |
| Связей нет, но прикрепление было | никто, до очистки |
| Старая загрузка без восстановленных связей и без известного факта прикрепления | только загрузивший |

Полностью публичного класса нет. Анонимный запрос получает 401.

## Порядок проверки

1. Запрос без действующей сессии — 401. После завершения #705 принимается только cookie
   `__Host-craneapp_session` (вне production — `craneapp_session`),
   через штатный механизм аутентификации, включая проверку отзыва токена.
   Поддержка `Authorization: Bearer` удалена вместе с переходным режимом #705. Облегчённого пути для скачивания нет.
2. Объект определяется по текущему порядку маршрута: сначала `media.uploads`,
   затем стикер или иконка пака. Для стикера проверяются существование его пака
   и подтверждённые `bucket/object_key`; для иконки — существование пака и
   `icon_bucket/icon_object_key`. В текущей модели приватных паков нет:
   управляемые объекты существующего пака доступны всем авторизованным,
   как содержимое пака через `GetStickers`. Ограничение списка паков владельцем
   не делает пак приватным. Отсутствующая или удалённая сущность либо объект
   без подтверждённых координат хранилища не выдаётся; возврата к прямому URL
   хранилища нет. Если появятся приватные паки, их ACL должна применяться
   одинаково к списку стикеров, скачиванию стикера и иконке.
3. Если у загрузки есть хотя бы одна действующая связь, права считаются только
   по связям. Права загрузившего при этом не учитываются: иначе отправитель,
   вышедший из чата, продолжал бы читать файл как автор загрузки.
   Достаточно одной действующей связи, разрешающей доступ. Потеря доступа через
   один чат не отзывает доступ через другую разрешённую связь того же файла.
4. Если действующих связей нет, доступ есть только у загрузившего и только при
   условии, что загрузка никогда не была прикреплена. Факт прикрепления
   хранится отдельно от строк связей и не снимается при их удалении: иначе
   удаление последнего сообщения возвращало бы отправителю доступ к вложению.
5. `HEAD` проверяется так же, как `GET`, и при отказе не раскрывает метаданные
   файла: имя, размер, MIME, диапазоны и валидаторы кэша. Коды ответов различают
   отсутствие сессии (401), отсутствие прав (403) и отсутствие объекта (404);
   скрытие самого факта существования от авторизованного пользователя модель
   не обещает.

`uploadId` остаётся идентификатором, а не bearer-секретом: знание id не даёт
права на скачивание. Scoped-токены в эту модель не входят и могут быть добавлены
позже под конкретный сценарий.

## Схема

`media.uploads`:

- `purpose` — `message | avatar | gif | sticker | unknown`, сохраняется при
  загрузке; `unknown` ставится бэкфиллом там, где назначение не определено
  достоверно. Назначение описывает замысел и не является основанием доступа.
- признак того, что загрузка когда-либо была прикреплена, — выставляется при
  создании первой связи и никогда не снимается.

`media.upload_refs` — связи с настоящими FK и индексами:

- `upload_id` → `media.uploads(id)`;
- `kind` — вид связи, с CHECK, что заполнена ровно одна ссылка,
  соответствующая виду;
- `message_id` → `messages.messages(id)`, `chat_id` → `chats.chats(id)`,
  либо владелец профиля, либо группа для её аватара, либо `gif_id`;
  для аватара группы отдельный `kind` и FK на `chats.chats(id)`;
- уникальность по паре загрузка плюс сущность; одна загрузка может иметь
  несколько связей, в том числе несколько сообщений.

`upload_refs` описывает только объекты из `media.uploads`. Стикеры и иконки
паков не получают фиктивные строки загрузок или связи с таким FK: их
основанием доступа служит собственная запись каталога и существующий пак.
При добавлении стикера либо иконки координаты хранилища записываются вместе
с сущностью; удаление сущности сразу прекращает выдачу через API, независимо
от срока физического удаления файла.

Все сервисы работают в одной базе `craneapp`, поэтому межсхемные FK возможны.
Если media когда-нибудь выделяется в отдельную базу, эти FK — та точка, где
понадобится отдельный механизм согласованности; межбазовый FK не
предполагается.

## Создание и снятие связей

- Связь с сообщением создаётся при отправке, в том же месте, где уже
  проверяется право отправителя прикрепить загрузку.
- Связь с аватаром профиля создаётся при установке аватара в профиле, с
  аватаром группы — при создании группы или обновлении её аватара, с публикацией
  в библиотеке GIF — при создании записи библиотеки.
- До создания любой связи проверяется право прикрепить загрузку. Для публикации
  в профиле, библиотеке GIF или аватаре группы требуется владение
  загрузкой; одного права скачать её или знания `uploadId` недостаточно.
  Дополнительно проверяется право менять целевую сущность (профиль или
  группу). Обработчики аватара принимают произвольный URL, поэтому для локальных
  `/api/v2/media/{uploadId}` проверка владельца загрузки должна быть добавлена
  явно до записи URL и связи. URL внешних ресурсов не создаёт `upload_refs`.
  `CreateGif` уже принимает только локальный путь загрузки и проверяет владельца,
  MIME `image/gif` и отсутствие шифрования. Эти проверки сохраняются;
  добавляется создание связи в транзакции с публикацией GIF.
  Проверка прав, изменение сущности, создание связи и выставление факта
  прикрепления выполняются в одной транзакции.
- Замена или удаление аватара профиля либо группы снимает старую связь;
  удаление публикации GIF, профиля или группы снимает соответствующие
  связи. Факт прежнего прикрепления остаётся. Доступ к аватару группы
  проверяется по текущему участию в группе на каждый запрос.
- Выход из чата закрывает доступ через этот чат: участие проверяется на каждый
  запрос.
- Удаление сообщения для всех снимает основание доступа через это сообщение.
- «Удалить у себя» — это скрытие в интерфейсе. Доступ к файлу оно не отзывает и
  связь не снимает.
- После отзыва или истечения сессии новые запросы получают 401 до проверки ACL.
  Владение загрузкой и участие в чате не заменяют действующую сессию.
- При удалении пользователя текущий FK `media.uploads.uploader_id` удаляет его
  загрузки каскадом, а вместе с ними — `upload_refs`. Их ID больше не выдаются
  через API (404 для другого авторизованного пользователя), даже если осталась
  старая ссылка в сообщении. Удаление физических объектов относится к #987.
- Проверки применяются к новым запросам. Уже начатая передача не прерывается,
  скачанные копии не отзываются.

## Range, HEAD, превью и кэш

- Незашифрованный объект: `Range` проксируется, 206 и 416 работают как сейчас.
- Зашифрованный объект отдаётся как JSON-конверт целиком, `Range` не
  поддерживается, ответ всегда 200. Это фиксируется в контракте; частичная
  расшифровка в задачу не входит.
- Превью и миниатюры наследуют права исходной загрузки, отдаются тем же
  маршрутом с той же проверкой и не получают отдельного неавторизованного
  пути. Сейчас миниатюр в системе нет ни на сервере, ни в контракте, ни в
  клиенте — правило фиксируется на будущее.
- Inline playback зашифрованных вложений идёт из blob: клиент скачивает файл
  целиком через API-клиент, поэтому плеер не обращается к серверу и `Range` ему
  не нужен. Незашифрованные файлы, которые играются прямо по адресу, идут
  обычным путём — с авторизацией, ACL и `Range`.
- Защищённые ответы исключаются из общего кэша: `Cache-Control: private, no-cache`,
  требующий проверки на сервере перед каждым повторным использованием ответа.
  Одного `private` без `max-age` недостаточно: частный кэш может назначить
  эвристический срок свежести. При отсутствии валидаторов выполняется обычный
  запрос; при их появлении проверка ACL предшествует ответу 304. Текущий
  `private, max-age=86400` на зашифрованном пути снимается, потому что он
  позволяет сутки отдавать файл без обращения к серверу.
- Условных запросов сейчас нет: `ETag` и `Last-Modified` из хранилища не
  проксируются. Если они появятся, 304 возвращается только после проверки прав.

## Rate limit

Добавляется группа `media-download` для `GET` и `HEAD`. Лимиты выбираются с
учётом того, что клиент грузит много картинок сразу. Новая группа не отменяет
глобальную корзину на IP, поэтому проверяется их совместное действие.

## Бэкфилл

- Назначение определяется по достоверным связям: запись библиотеки GIF, аватар
  в `users.profiles.avatar_url`, аватар группы в `chats.chats.avatar_url`,
  ссылка в метаданных сообщения. Для сообщений `chat_id` выводится
  из самого сообщения один раз в миграции.
- Стикеры и иконки паков обрабатываются отдельно от бэкфилла загрузок:
  используются подтверждённые координаты хранилища из #973 и собственные ID.
  Они не переводятся в `purpose = unknown`; объекты без подтверждённых
  координат остаются недоступными.
- Для чего связь не выводится — `purpose = unknown` и доступ только
  загрузившему. Неизвестное сохраняется как неизвестное, а не домысливается.
- Принятый риск: старая загрузка, которая была прикреплена к уже удалённому
  сообщению, попадёт в `unknown` и останется доступной загрузившему. Отличить
  её от загрузки, которая никогда не отправлялась, по текущим данным нельзя.

## Контракт и тесты

- У `get` и `head` появляется `security: *secure` через существующий YAML-якорь
  `x-secure`, добавляются 401 и 403.
- 401 возвращается без действующей cookie-сессии, 403 — для существующего
  объекта без разрешённой связи или права владельца, 404 — для отсутствующего
  объекта либо каталога без подтверждённых координат хранения. Дополнительная
  Bearer-аутентификация не вводится.
- Описывается, что `uploadId` не является capability и что `Range` не
  поддерживается для зашифрованного конверта.
- Тесты покрывают матрицу: аноним, посторонний авторизованный, участник чата,
  вышедший участник, отправитель после выхода, владелец неприкреплённой
  загрузки, владелец ранее прикреплённой загрузки без связей, аватар профиля, аватар
  группы (участник, посторонний и вышедший участник), гифка, стикер и иконка
  пака без строки в `media.uploads` — каждый
  случай для `GET` и для `HEAD`.
- Отдельно проверяются отказ публикации чужого `uploadId` через аватар профиля,
  аватар группы и GIF, снятие связи при замене аватара, бэкфилл аватаров
  групп и повторное обращение после отзыва доступа с учётом заголовков кэша.
- Для стикеров и иконок проверяются аноним, владелец и другой авторизованный,
  удалённый пак, удалённый стикер и отсутствие подтверждённых координат
  хранилища. Ни одна ветка маршрута не обходит сессию, ACL, кэш или rate limit.

## Раскатка

Переходного режима с анонимной выдачей нет. Порядок: проверить и при
необходимости обновить поддерживаемые клиенты, затем включить защиту. После
включения анонимный запрос получает 401. Сбор статистики, если нужен, делается
до переключения и на ограниченный срок.

Что проверить на клиентах перед включением:

- веб тянет вложения чата через свой API-клиент с `credentials: same-origin`
  и cookie сессии (#705);
- аватары в вебе вставляются прямо в `<img src>` и зависят от cookie;
- legacy-клиент кладёт адрес медиа в иконку браузерного уведомления
  (`browserNotifications.js`), а её грузит сам браузер — передача cookie там не
  гарантирована.

Одного `SameSite=Lax` недостаточно, чтобы считать это проверенным.

## Вне этой модели

- Удаление объектов в хранилище и очистка сирот — обязательная реализация
  согласованного правила в отдельной #987, за пределами документационной #615.
  В #987 добавлены транзакционные задания для загрузок, снятия связей,
  soft delete сообщений и удаления каталога. Удаление автора больше не удаляет
  запись загрузки: uploader становится NULL, координаты и общие ссылки сохраняются.
  Worker повторно проверяет живые upload_refs и координаты каталога, затем
  фиксирует начало удаления. Прикрепление и начало удаления сериализуются по
  координатам объекта; после начала удаления новые прикрепления запрещены,
  включая время повторных попыток. После успешного удаления файла строки uploads
  удаляются; отметка начала удаления сохраняется и запрещает повторное использование ключа.
  Неприкреплённые новые загрузки получают задание на **7 суток** после создания
  (согласовано владельцем при реализации #987). Worker повторно проверяет срок;
  отсутствие автора позволяет убрать неприкреплённый файл без ожидания TTL.
  При живых ссылках задание откладывается на 5 минут, ошибки storage повторяются
  с существующим backoff. Транзакционный триггер последнего снятия ссылки
  ускоряет уже существующее задание. Старые uploads автоматически в TTL-очередь
  миграцией не добавляются: они входят в историческую инвентаризацию ниже.
- Перенос имени файла в зашифрованную часть сообщения — отдельное усиление
  конфиденциальности. Сейчас конверт зашифрованной загрузки отдаёт `fileName`,
  `mimeType`, `sizeBytes` и `iv` открытым текстом; авторизация и ACL закрывают
  это от посторонних, но не от сервера.
- Scoped download tokens.

## Реализация

- **#986 / PR #995 — выполнено:** сессия и ACL на скачивании, `purpose`,
  таблица связей, факт прикрепления, заголовки кэша, группа `media-download`, контракт и тесты,
  бэкфилл и проверка доступа к стикерам и иконкам паков без `media.uploads`.
  Реализованная часть сохраняет данные для #987 — факт прикрепления и
  возможность определить потерю последней ссылки. Доступ по ACL не ждёт
  физической очистки хранилища.
- **#987 — реализация очистки:** транзакционная очередь, повторная проверка
  ссылок, TTL 7 суток, защита attach/cleanup и read-only инвентарь исторических
  сирот. Само разовое удаление исторических объектов требует отдельной сверки
  и не запускается миграцией или командой инвентаризации.

#615 закрывается после фиксации этой модели и ссылок на отдельные задачи
реализации. #986 уже выполнена; физическая очистка из #987 остаётся обязательной
отдельной работой и не считается выполненной при закрытии #615.


## Исторические сироты: только инвентаризация (#987)

Из `backend-v2/`, с явно заданными `DATABASE_URL`, `MINIO_ENDPOINT`,
`MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MEDIA_BUCKET` (и при необходимости
`MINIO_REGION`):

```sh
go run ./cmd/media-orphans > media-orphans.jsonl
```
