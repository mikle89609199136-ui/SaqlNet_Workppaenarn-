# Политика rate limiting для edge gateway

Этот документ описывает целевую начальную политику ограничения запросов в edge
gateway. Она должна защищать сервисы от перебора паролей, спама и аномальной
нагрузки, но не мешать обычной работе клиента.

Приведённые ниже значения являются отправной точкой, а не окончательными
порогами. После реализации их нужно проверить на обычных пользовательских
сценариях, нагрузочными тестами и по метрикам ответов `429`.

## Как работает ограничение

Для каждой группы используется алгоритм token bucket:

- `rate` задаёт скорость пополнения корзины и допустимую длительную нагрузку;
- `burst` задаёт максимальное количество токенов в полной корзине;
- один запрос расходует один токен.

Например, `10 запросов/мин` означает, что корзина получает один новый токен
примерно каждые 6 секунд. Это не означает жёсткий предел в 10 запросов в любом
минутном окне: после простоя клиент сначала может использовать накопленный
`burst`.

Для запроса, который попал в отдельную маршрутную группу, проверяются две
корзины:

1. В корзине своей группы, например `message-read` или `media-upload`.
2. В общей глобальной корзине.

Запрос проходит только тогда, когда токен есть в обеих корзинах. Групповая
корзина ограничивает конкретный вид действий, а глобальная — сумму всех
действий с одного IP. Маршруты документации не имеют отдельной групповой
корзины и проверяются только глобальным лимитом.

Проверка и расходование токенов групповой и глобальной корзин должны быть
атомарными: запрос либо получает по одному токену из обеих корзин, либо не
расходует токены ни в одной из них. Если глобальная корзина отклоняет запрос,
токен групповой корзины не должен быть списан, и наоборот. Реализация через два
последовательных вызова `Allow`, где первый вызов сразу расходует токен, не
соответствует этой политике без механизма резервирования и отката.

## Ключ лимитирования

Edge gateway не проверяет JWT и не располагает подтверждённым идентификатором
пользователя. Поэтому все его корзины используют доверенный IP клиента:

```text
(доверенный IP, группа маршрута)
```

Например, для одного IP независимо существуют корзины `login-register`,
`message-write` и `message-read`. Глобальная корзина также создаётся отдельно
для каждого доверенного IP.

Edge учитывает заголовок `X-Forwarded-For` только тогда, когда непосредственный
отправитель запроса входит в список доверенных reverse proxy. Список задаётся
переменной окружения `TRUSTED_PROXIES`: поддерживаются отдельные IP-адреса и
CIDR-сети, разделённые запятыми.

```env
TRUSTED_PROXIES=127.0.0.1,10.0.0.0/24
```

Цепочка `X-Forwarded-For` обрабатывается справа налево до первого недоверенного
адреса — он считается IP клиента. Если непосредственный отправитель не является
доверенным proxy, заголовок отсутствует или содержит некорректное значение,
используется IP из `RemoteAddr`.

Пустое значение `TRUSTED_PROXIES` является безопасным значением по умолчанию:
edge не доверяет ни одному proxy и всегда использует `RemoteAddr`. Некорректный
IP-адрес, CIDR или пустой элемент списка останавливает запуск edge с ошибкой.
Конкретные адреса и сети необходимо задавать в соответствии с production-
инфраструктурой. Если reverse proxy перед edge отсутствует, значение следует
оставить пустым.

Ограничение по IP является грубой защитой gateway: несколько пользователей за
одним NAT делят общую корзину, а распределённая атака может использовать разные
IP. При необходимости auth и другие сервисы должны дополнительно ограничивать
чувствительные операции по подтверждённому аккаунту.

## Начальные лимиты

| Группа                    |            Rate | Burst | Ключ                   |
| ------------------------- | --------------: | ----: | ---------------------- |
| Вход и регистрация        | 10 запросов/мин |     5 | доверенный IP + группа |
| Пароль и 2FA              | 10 запросов/мин |     5 | доверенный IP + группа |
| Остальные auth            | 30 запросов/мин |    10 | доверенный IP + группа |
| Проверка юзернейма        |     2 запроса/с |     5 | доверенный IP + группа |
| Запись сообщений          |    5 запросов/с |    20 | доверенный IP + группа |
| Чтение сообщений          |   20 запросов/с |    40 | доверенный IP + группа |
| Загрузка медиа            | 60 запросов/мин |    30 | доверенный IP + группа |
| Звонки                    | 30 запросов/мин |    15 | доверенный IP + группа |
| MLS                       |    5 запросов/с |    10 | доверенный IP + группа |
| Остальные API             |   20 запросов/с |    40 | доверенный IP + группа |
| WebSocket handshake       | 10 запросов/мин |    20 | доверенный IP + группа |
| Глобальный защитный лимит |   50 запросов/с |   100 | доверенный IP          |

### Сопоставление маршрутов

Маршрут определяется по HTTP-методу и пути. Более узкие правила проверяются
раньше общих.

#### Вход и регистрация

- `POST /api/v2/auth/login`;
- `POST /api/v2/auth/register`.

#### Пароль и 2FA

- `POST /api/v2/auth/change-password`;
- `POST /api/v2/auth/2fa/enable`;
- `POST /api/v2/auth/2fa/disable`;
- `POST /api/v2/auth/2fa/verify`.

#### Остальные auth

Все остальные маршруты `/api/v2/auth/**`, которые не вошли в две предыдущие
группы. Сюда относятся управление сессиями и токенами, статус 2FA, публичный
ключ и QR-вход.

#### Проверка юзернейма

- `GET /api/v2/users/check-username`.

Правило совпадает по полному пути и методу, поэтому остальные маршруты
`/api/v2/users/**` под него не попадают и остаются в группе остальных API.
Запрос тем же путём с другим методом сервис `users` отклоняет сам (`405`), и для
edge это обычный запрос группы остальных API.

#### Запись сообщений

- `POST /api/v2/messages/read`;
- `POST /api/v2/messages/{chatId}`;
- `PUT|DELETE /api/v2/messages/{messageId}`;
- `POST /api/v2/messages/{messageId}/reactions`;
- `POST|DELETE /api/v2/messages/{messageId}/favorite`;
- `POST /api/v2/chats/{chatId}/read`;
- `POST /api/v2/chats/{chatId}/messages/delete`;
- `POST|DELETE /api/v2/chats/{chatId}/pins/{messageId}`.

#### Чтение сообщений

- `GET /api/v2/messages/{chatId}`;
- `GET /api/v2/messages/search`;
- `GET /api/v2/messages/favorites`;
- `GET /api/v2/messages/{messageId}/reactions`;
- `GET /api/v2/chats/{chatId}/pins`.

#### Загрузка медиа

- `POST /api/v2/media`.

Одно вложение — одна загрузка. Композер разрешает приложить до десяти файлов
за раз, и каждый уходит отдельным запросом; голосовое сообщение и аватар в
профиле — тоже отдельные загрузки. Поэтому burst рассчитан на полное действие
композера с запасом на нескольких клиентов за общим IP.

Ограничение считает запросы, а не объём переданных данных. Оно не заменяет
серверный предел размера файла, ограничение параллельных загрузок и квоты
хранилища.

#### Звонки

Все маршруты `/api/v2/calls/**`:

- `GET /api/v2/calls/ice-servers`;
- `GET|POST /api/v2/calls/rooms`;
- `GET /api/v2/calls/rooms/{id}`.

#### MLS

Все маршруты `/api/v2/mls/**`: загрузка и выдача KeyPackage, состояние группы,
`commit` и `welcome`.

Границу IP здесь нужно понимать как первый, грубый слой. Edge не проверяет токен
и не знает пользователя, поэтому не может считать запросы по пользователю или по
адресату, а именно это нужно для двух угроз ниже. Точный лимит должен жить в
сервисе `chat`, где пользователь уже известен.

#### Остальные API

Все остальные маршруты `/api/v2/**`, которые не подошли под более узкое
правило. Это резервная защита для существующих и новых API. Если отдельная
операция окажется особенно дорогой или подверженной злоупотреблению, её следует
вынести в собственную группу.

Маршруты Web Push, `GET /api/v2/users/push/vapid-key` и
`POST|DELETE /api/v2/users/push/subscriptions`, сознательно остаются в этой
группе. Клиент обращается к ним раз за запуск приложения (подтверждение
подписки) и при включении или выключении уведомлений, а не по таймеру. Запись
подписки ограничена самим сервисом: тело запроса не больше 8 КБ, у одного
пользователя не больше 20 подписок, лишние старые удаляются при вставке, так
что таблицу одним аккаунтом не раздуть. Дорогих внешних вызовов эти маршруты
не делают. Если появится причина считать их иначе, их следует вынести в
собственную группу.

#### Документация

Маршруты `/docs/**` не имеют отдельного лимита. OpenAPI-файлы встроены в
исполняемый файл edge gateway и не обращаются к БД или внутренним сервисам,
поэтому для них достаточно глобальной корзины.

#### WebSocket

Группа применяется к `GET /ws` только до переключения HTTP-соединения на
WebSocket. Сообщения внутри уже установленного соединения эта политика не
считает.

#### Глобальный лимит

Глобальная корзина применяется ко всем `/api/v2/**`, `/docs/**` и к handshake
`GET /ws`. Она не складывается с групповым rate: запрос должен отдельно получить
разрешение своей группы и глобальной корзины.

## Настройка через переменные окружения

Каждая корзина настраивается двумя переменными окружения:

```text
EDGE_RATE_LIMIT_<ГРУППА>_RATE    — скорость пополнения, число с единицей
EDGE_RATE_LIMIT_<ГРУППА>_BURST   — ёмкость корзины, целое число токенов
```

| Группа                    | `<ГРУППА>`       | Дефолтный rate | Дефолтный burst |
| ------------------------- | ---------------- | -------------- | --------------: |
| Вход и регистрация        | `LOGIN_REGISTER` | `10/min`       |               5 |
| Пароль и 2FA              | `PASSWORD_2FA`   | `10/min`       |               5 |
| Остальные auth            | `OTHER_AUTH`     | `30/min`       |              10 |
| Проверка юзернейма        | `USERNAME_CHECK` | `2/s`          |               5 |
| Запись сообщений          | `MESSAGE_WRITE`  | `5/s`          |              20 |
| Чтение сообщений          | `MESSAGE_READ`   | `20/s`         |              40 |
| Загрузка медиа            | `MEDIA_UPLOAD`   | `60/min`       |              30 |
| Звонки                    | `CALLS`          | `30/min`       |              15 |
| MLS                       | `MLS`            | `5/s`          |              10 |
| Остальные API             | `OTHER_API`      | `20/s`         |              40 |
| WebSocket handshake       | `WEBSOCKET`      | `10/min`       |              20 |
| Глобальный защитный лимит | `GLOBAL`         | `50/s`         |             100 |

### Единица измерения указывается в значении

`RATE` задаётся числом вместе с единицей, через косую черту:

```env
EDGE_RATE_LIMIT_LOGIN_REGISTER_RATE=10/min
EDGE_RATE_LIMIT_MESSAGE_WRITE_RATE=5/s
```

Допустимые единицы: `s`, `sec`, `second`, `min`, `minute`, `h`, `hour`. Регистр и
пробелы вокруг частей значения не важны.

Единица обязательна. Значение без единицы останавливает запуск edge с ошибкой:

```text
environment variable EDGE_RATE_LIMIT_LOGIN_REGISTER_RATE: rate "10" has no unit,
expected a value like "10/min" or "5/s"
```

Так сделано намеренно. Лимиты политики различаются примерно в 300 раз — от
`10/min` до `50/s` — поэтому редкие операции удобно записывать в минутах, а
частые в секундах, и одна общая единица делала бы половину таблицы нечитаемой.
Пока единица была неявной договорённостью («в переменной всегда секунды»),
значение `10`, записанное в смысле «10 в минуту», молча ослабляло лимит в 60
раз: число корректное, ошибки нет, сервис работает. Требование указать единицу
убирает ту операцию, в которой люди ошибались, — перевод в голове.

Ноль, отрицательное значение, `NaN`, бесконечность, неизвестная единица и
нечисловое значение тоже останавливают запуск. `BURST` — количество токенов,
единицы у него нет, он задаётся целым положительным числом.

### Где живут значения по умолчанию

Дефолты заданы ровно в одном месте — в `loadRateLimitConfig()`
(`backend-v2/cmd/edge/rate_limit_config.go`), где они записаны в тех же единицах,
что и в таблице выше:

```go
loginRegister: loadBucketConfig("LOGIN_REGISTER", perMinute(10), 5),
messageWrite:  loadBucketConfig("MESSAGE_WRITE", perSecond(5), 20),
```

`docker-compose.yml` пробрасывает все переменные в контейнер с пустым значением
по умолчанию:

```yaml
- EDGE_RATE_LIMIT_MESSAGE_WRITE_RATE=${EDGE_RATE_LIMIT_MESSAGE_WRITE_RATE:-}
```

Пустая строка означает «дефолт из кода». Это сделано намеренно, чтобы дефолт не
дублировался в compose и не разошёлся с кодом при следующем изменении политики.
Чтобы переопределить лимит, достаточно задать переменную в `.env` или в окружении
деплоя — править compose отдельно не нужно.

### Действующие лимиты видны в логе

При старте edge печатает лимиты, с которыми он реально работает:

```text
edge rate limits (rate in tokens per second, burst in tokens):
  login-register      0.167/s  (    10.0/min)  burst 5
  username-check      2.000/s  (   120.0/min)  burst 5
  message-write       5.000/s  (   300.0/min)  burst 20
  global             50.000/s  (  3000.0/min)  burst 100
```

Это единственный способ снаружи проверить, что настройка применилась.
Переменная, не дошедшая до контейнера, выглядит точно так же, как незаданная:
сервис запускается и работает, просто с другими лимитами. Лог показывает
действующие значения в обеих единицах, поэтому и потерянная настройка, и
перепутанная единица видны сразу после запуска.

## Почему выбраны такие значения

- Вход и регистрация доступны без авторизации, выполняют работу с хешем пароля
  и могут использоваться для перебора или массового создания аккаунтов. Burst
  `5` оставляет несколько попыток на опечатки и общий IP, а постоянная скорость
  остаётся низкой.
- Смена пароля и операции 2FA также используют хеширование или проверку пароля,
  поэтому вынесены из остальных auth-маршрутов в отдельную строгую группу.
- Остальные auth в основном связаны с чтением и управлением сессиями. Их лимит
  выше, но значение `30 запросов/мин` необходимо уточнить, если клиент начнёт
  периодически опрашивать статус QR-входа.
- Проверка юзернейма доступна без авторизации и отвечает на вопрос, существует
  ли аккаунт с таким именем. По ней можно перечислить пользователей: словарь имён
  прогоняется по эндпоинту, а на выходе получается список реальных аккаунтов —
  и как утечка сама по себе, и как заготовка для подбора паролей по
  подтверждённым логинам. Поэтому у группы свой строгий лимит, а не общий с
  остальными API. Значения выбраны с запасом к тому, что нужно клиенту: форма
  регистрации отправляет запрос через 400 мс после того, как пользователь
  перестал печатать, и кеширует ответ на 30 секунд, поэтому живой сценарий
  укладывается в единицы запросов на имя.
- Запись сообщений изменяет данные и может вызывать WebSocket-рассылку. Rate
  `5 запросов/с` ограничивает постоянный спам, а burst `20` допускает короткие
  серии действий, в том числе пересылку нескольких сообщений.
- Чтение выполняется чаще записи и может происходить параллельно при открытии
  чата. Rate `20 запросов/с` и burst `40` оставляют запас для нескольких
  клиентов за одним IP, но ограничивают постоянную нагрузку на БД и сеть.
- Загрузка медиа расходует сеть и хранилище. Значения подобраны под то, как
  клиент шлёт файлы сегодня: до десяти вложений за одно нажатие «отправить»,
  каждое отдельным запросом, плюс голосовые сообщения и аватар. Burst `30`
  покрывает полное действие композера и оставляет запас нескольким клиентам за
  общим IP; rate `60 запросов/мин` не мешает переписке голосовыми. Постоянное
  заполнение хранилища этой корзиной не ограничить — она считает запросы, а не
  байты, и для этого нужны квоты и предел размера файла.
- MLS вынесен в свою группу по двум причинам. Во-первых, `commit` и `welcome`
  обращаются к внешнему crypto-сервису, поэтому один запрос к edge порождает
  запрос к другому сервису; нагрузочными тестами crypto эту стоимость ещё нужно
  подтвердить. Во-вторых, `GET /api/v2/mls/keypackages/{userId}` не просто
  читает, а удаляет выданный KeyPackage: они одноразовые, и серия запросов может
  исчерпать запас адресата (загрузить можно не больше 20 за раз), после чего его
  перестанут добавлять в новые группы. Проверка «есть общий чат» сужает круг
  целей, но не число запросов. Значения `5/s` и burst `10` взяты как начальные и
  их нужно скорректировать по реальной нагрузке. На момент введения клиент эти
  маршруты не вызывает, поэтому лимит никого не ограничивает.
- Звонки вынесены в свою группу, потому что `POST /api/v2/calls/rooms` на каждый
  вызов пишет строку в `calls.rooms` и заводит запись в памяти процесса, и ни то
  ни другое не ограничено сверху. Установка одного звонка стоит нескольких
  запросов группы, поэтому burst `15` оставляет запас на серию попыток
  дозвониться, а rate `30 запросов/мин` ограничивает рост таблицы и карты комнат.
  Остальные маршруты группы обслуживают установку соединения и вызываются реже.
- Группа остальных API нужна как резервная защита. Её лимит достаточно мягок
  для параллельной загрузки профиля, чатов, настроек и ключей при запуске
  приложения.
- WebSocket обычно устанавливается один раз и живёт долго. Низкий rate
  ограничивает циклы переподключения, а burst `20` позволяет нескольким клиентам
  за общим IP восстановить соединение после краткого сбоя.
- Глобальный лимит ограничивает суммарную нагрузку, даже если запросы остаются в
  пределах каждой отдельной группы. Burst `100` допускает короткую пачку при
  запуске нескольких клиентов за одним IP.

## Исключения

Политика не применяется к:

- `/health/live`;
- CORS preflight-запросам `OPTIONS`;
- статическим frontend-файлам.

Проверка исключений должна происходить до расходования токенов.

## Ответ при превышении лимита

Gateway возвращает HTTP `429 Too Many Requests` в общем формате ошибок API:

```json
{
  "code": "rate_limited",
  "message": "too many requests"
}
```

Ответ содержит `Retry-After` с целым количеством секунд до рекомендуемой
повторной попытки. Клиент не должен немедленно повторять отклонённый запрос. Для
автоматических повторов используется exponential backoff с небольшим случайным
отклонением (jitter).

Это особенно важно для массовой пересылки: текущий frontend отправляет отдельный
HTTP-запрос для каждого сообщения, поэтому серия длиннее доступного burst должна
корректно обрабатывать `429` и продолжаться после ожидания.

## Проверка и пересмотр

До релиза необходимо проверить обычные сценарии:

- запуск приложения и параллельную загрузку начальных данных;
- вход с несколькими ошибками в пароле;
- быстрое переключение чатов и загрузку истории;
- отправку, реакции и массовую пересылку сообщений;
- загрузку нескольких медиафайлов;
- одновременное WebSocket-переподключение нескольких клиентов за одним IP.

Отдельно проверяется граница каждой корзины: запросы в пределах burst проходят,
следующий запрос получает `429`, а после восстановления токена запрос снова
разрешается.

Нагрузочные тесты выполняются только в разрешённом тестовом окружении. После
включения политики по каждой группе собираются:

- общее количество запросов и ответов `429`;
- задержка ответов;
- нагрузка на edge, внутренние сервисы и БД.

В метрики и логи нельзя записывать токены авторизации, содержимое сообщений и
другие чувствительные данные. Лимиты пересматриваются, если нормальные сценарии
регулярно получают `429` или нежелательная нагрузка всё ещё заметно влияет на
сервисы.

## Несколько экземпляров edge gateway

Счётчики хранятся в памяти процесса: каждый `tokenBucket` держит свою
`map[доверенный IP → корзина]`. Они не персистятся и не разделяются между
процессами.

Из этого следует:

- При `N` репликах edge за балансировщиком у каждой реплики свой независимый
  набор корзин. Запросы одного клиента распределяются между репликами (как
  именно — зависит от алгоритма балансировщика), поэтому в худшем случае
  эффективный лимит на IP приближается к `N`-кратному от настроенного. При
  sticky-сессиях он ближе к однократному, но отказ одной реплики перекидывает её
  трафик на остальные.
- Рестарт или деплой реплики обнуляет её корзины. Клиенты, которых она
  обслуживала, получают полный `burst` заново.
- Глобальная защитная корзина при этом тоже становится `N`-кратной и остаётся
  лишь грубым backstop’ом, а не точным пределом на кластер.

Точный общий лимит на весь кластер требует внешнего хранилища состояния —
например token bucket в Redis с атомарным обновлением (Lua-скрипт) или
отдельного сервиса лимитирования. Это сознательно вне области текущей задачи;
политика не навязывает конкретное хранилище.

Пока такого хранилища нет, лимиты задаются с учётом числа реплик (делить целевое
значение на `N`) либо принимается более слабая верхняя граница как осознанный
компромисс.

## Связь с реализацией

Документ описывает целевое поведение. Текущая реализация edge gateway безопасно
определяет IP клиента с учётом `TRUSTED_PROXIES`, применяет конфигурируемые
лимиты для всех перечисленных маршрутных групп и глобальной корзины, атомарно
проверяет групповую и глобальную корзины и возвращает `Retry-After` при `429`.

Лимиты задаются переменными окружения с обязательной единицей измерения и
печатаются в лог при старте.

Не реализовано только разделение счётчиков между экземплярами edge gateway — см.
раздел «Несколько экземпляров edge gateway» выше.
