# Временный деплой на Vercel

Ветка: `hotfix/vercel-deploy`. Не сливать настройки временного хостинга в
`master`; ветку сохранять. Новые изменения приложения переносить из `master`
обычным merge, сохраняя конфигурацию Vercel.

## Фронтенд

В проекте Vercel выбрать Root Directory `frontend`, Framework `Vite`, Node.js
22.x. Удалить ручные overrides Build Command и Output Directory, если они
были заданы: настройки находятся в `frontend/vercel.json`.

Команда сборки: `npm run build -- --outDir dist`, результат: `frontend/dist`.
Обычная сборка для Docker по-прежнему создаёт корневой `dist`.
SPA fallback исключает `/api` и `/ws`, чтобы ошибки подключения сервера
не превращались в HTML с кодом 200. `sw.js` и `version.json` не кешируются.

После push создать preview ветки, затем выбрать её в
Settings → Environments → Production → Branch Tracking.

## Подключение сервера — обязательный следующий шаг

Эта конфигурация собирает только frontend. Она не запускает Go/Rust-сервисы
и не создаёт PostgreSQL, Redis, NATS или объектное хранилище.

До использования приложения нужно выбрать размещение backend и настроить
маршруты `/api/v2` и `/ws` на том же публичном хосте, что и frontend.
Cookie сессии в production — HttpOnly, Secure, SameSite=Lax, с префиксом
`__Host-`. API-клиент отправляет cookies только на свой origin, поэтому
просто задать внешний `VITE_API_BASE_URL` недостаточно для рабочего входа.
Внешний адрес `VITE_SOCKET_URL` также не получит cookie другого хоста.

Добавить точный публичный origin в `ALLOWED_ORIGINS` backend; не отключать
проверку Origin. Секреты backend не добавлять в переменные `VITE_*`.

После подключения проверить регистрацию/вход, перезагрузку страницы чата,
обмен сообщениями между двумя сессиями, переподключение WebSocket, загрузку
медиа, звонки и выход из аккаунта. Успешная сборка frontend не проверяет эти
сценарии.

Для ухода с Vercel переключить хостинг на `master`. Настройки находятся в
отдельной ветке, откатывать код приложения в `master` не требуется.
