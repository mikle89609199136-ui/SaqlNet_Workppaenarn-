# Временный деплой всего приложения на Vercel

Ветка `hotfix/vercel-deploy` сохраняется и не сливается в `master`.
Новые изменения приложения переносить из `master` обычным merge.

## Структура

Корневой `vercel.json` описывает два сервиса: Vite frontend и backend-контейнер
из `Dockerfile.vercel`. В контейнере supervisord запускает Go-сервисы edge,
auth, user, chat, media, admin и Rust crypto. Внутренние HTTP-соединения идут
по loopback. Публичные `/api/*`, `/ws`, `/health/*`, `/docs/*` направляются в
edge; остальные пути — во frontend. Cookie авторизации и WebSocket остаются
на одном публичном хосте. `VITE_API_BASE_URL` и `VITE_SOCKET_URL` не задавать.

Это временная упаковка существующего backend без изменения основного кода.
Services, Container Runtime и WebSockets на Vercel находятся в beta.
Контейнеры масштабируются и выключаются при отсутствии запросов; память и
локальные файлы не являются постоянным хранилищем. Фоновые задачи работают
только пока инстанс активен. WebSocket ограничен длительностью функции;
клиент уже умеет переподключаться. Полную работу звонков и фоновых уведомлений
необходимо проверить на реальном preview.

## Настройки проекта

1. Изменить Root Directory с `frontend` на корень репозитория (`./`).
2. Выбрать Services; убрать ручные overrides сборки и output directory.
   Всё задано в корневом `vercel.json`.
3. Для frontend выбрать Node.js 22.x. Сборка создаёт `frontend/dist`;
   обычная Docker-сборка приложения по-прежнему создаёт корневой `dist`.
4. В Environment Variables добавить значения из `deploy/vercel/.env.example`.
   Пример содержит заглушки, реальные секреты не хранить в Git.
5. Создать deployment ветки `hotfix/vercel-deploy`, затем выбрать её в
   Settings → Environments → Production → Branch Tracking.

## Внешние зависимости

Нужны доступные по сети PostgreSQL, Redis (протокол Redis, не REST API),
NATS и S3-совместимое хранилище с path-style URL и правами для проверки/
создания bucket, чтения, записи и удаления объектов. Не использовать
localhost для этих ресурсов. Preview должен использовать отдельные тестовые
ресурсы, чтобы не менять production-данные.

PostgreSQL-соединение должно поддерживать LISTEN/NOTIFY: использовать прямой
адрес базы или session pooling, не transaction pooling. Redis/NATS используются backend как внешние зависимости, а медиа
хранятся вне контейнера. Клиент NATS в этой ветке заменён официальным
клиентом: поддерживает TLS, пароль в URL и переподключения; outbox помечает
событие отправленным только после flush соединения.
Для звонков также нужны действующие TURN-настройки METERED_API_KEY и
METERED_DOMAIN; Web Push включается ключами VAPID.

ALLOWED_ORIGINS — точный публичный origin фронтенда (без пути), включая
preview origin при его проверке. Не использовать `*` и не отключать Origin
проверку. CRYPTO_SIGNING_SECRET должен совпадать с текущим ключом подписи,
если требуется сохранить ранее выданные сессии. CRYPTO_ENCRYPTION_SECRET
сохранять при переносе уже зашифрованных данных.

## Миграции перед первым запуском

Миграции не выполняются при сборке или холодном старте: это отдельный
однократный шаг для выбранной базы после резервного копирования.

```sh
docker build -f Dockerfile.vercel -t craneapp-vercel:local .
# DATABASE_URL экспортируется локально безопасным способом, не пишется в Git.
docker run --rm -e DATABASE_URL --entrypoint /usr/local/bin/migrate craneapp-vercel:local
```

Образ содержит /app/migrations, рабочая папка мигратора — /app. Не запускать
миграции одновременно. Перенос старых данных и файлов не выполняется этим
деплоем автоматически. AUTH_LOGOUT_ALL_GENERATION_ENABLED оставить false
до завершения совместимого обновления всех компонентов.

## Проверка и уход с Vercel

После миграций и деплоя проверить /health/live, регистрацию/вход, прямой URL
чата и перезагрузку, сообщения между двумя аккаунтами, переподключение WS,
загрузку медиа, звонки и выход. При проверке масштабирования убедиться, что
сообщения приходят между разными инстансами. Успешная сборка не подтверждает
эти сценарии. Секреты не должны попадать в переменные VITE_*.

Для ухода с Vercel переключить новый хостинг на `master`; откатывать
основной код не потребуется. Ветку и её историю оставить для воспроизводимости.

Документация платформы:
- https://vercel.com/docs/services
- https://vercel.com/docs/functions/runtimes/container
- https://vercel.com/docs/functions/websockets

Локальная проверка конфигурации: схема vercel.json прошла проверку, frontend
и backend-образ собраны, `go test ./...` прошёл. На отдельной локальной базе
проверены миграции, readiness всех backend-сервисов, регистрация, вход и
WebSocket handshake через edge с production-cookie. Реальный деплой на Vercel,
звонки и обмен сообщениями между инстансами этим не проверены.

## Безопасная диагностика переменных

Из корня репозитория (после `npm ci`):

```sh
node scripts/check-deployment-env.cjs
node scripts/check-deployment-env.cjs --env-file /path/to/private.env --check
```

Переменные процесса имеют приоритет над файлом. Команда выводит адреса и
порты, наличие логина/пароля и обязательных параметров, но скрывает значения
секретов. `--check` проверяет TCP-доступность всех адресов и делает `SELECT 1`
в PostgreSQL с проверкой авторизации. Для Redis, NATS и S3 это только TCP,
не проверка TLS или прав доступа. Отсутствующие настройки/ошибки дают exit 1.
Локальный `.env` не является источником production-секретов: реальные значения
нужно брать из настроек окружения текущего хостинга. Не публиковать их в логах.
