# CraneApp — работа с git

Практическое руководство: что делать по шагам и что делать, когда что-то пошло не так.

Правила и требования — в `02-git-workflow-v2.md`.

---

## 1. Разовая настройка

```bash
git clone https://github.com/mikle89609199136-ui/CraneApp.git
cd CraneApp
npm install                  # инструменты репозитория
cd frontend && npm ci        # зависимости клиента
cd ..
```

`npm install` в корне ставит git-хуки через lefthook. Проверьте:

```bash
ls .git/hooks/               # ожидаются pre-commit и commit-msg
```

Настройки, снимающие типовые проблемы:

```bash
git config pull.rebase true          # pull без merge-коммитов
git config push.autoSetupRemote true # push новой ветки без --set-upstream
git config rerere.enabled true       # запоминает разрешённые конфликты
git config core.autocrlf input       # только Windows: в репозитории всегда LF
```

## 2. Цикл работы над задачей

### 2.1 Взять задачу

Задача должна быть в статусе `Ready`, без метки `needs-triage`, с критериями приёмки. Если чего-то не хватает — не начинайте, спросите у владельца направления.

Назначьте себя, переведите в `In Progress`.

### 2.2 Создать ветку

**Всегда от свежего `master`.** Ветки от веток не создаются.

```bash
git switch master
git pull
git switch -c fix/174-forward-attachments
git push -u origin fix/174-forward-attachments
```

Формат: `<type>/<номер задачи>-<краткое описание латиницей>`.

| Тип задачи | Префикс |
| ------------------------ | ---------- |
| исправление ошибки | `fix/` |
| новая функциональность | `feat/` |
| рефакторинг | `refactor/` |
| тесты | `test/` |
| документация | `docs/` |
| производительность | `perf/` |
| сборка, зависимости | `build/` |
| CI/CD | `ci/` |
| прочее техническое | `chore/` |

Отправляйте ветку сразу — так коллеги видят, что задача взята.

### 2.3 Коммитить

Небольшими логическими шагами, а не одним куском в конце дня.

```bash
git add <файлы>
git commit -m "fix(msg): keep attachments on forward (#174)"
git push
```

Формат: `<type>(<scope>): <описание на английском> (#<номер задачи>)`.

Scope — область кода: `auth` `chat` `msg` `media` `call` `user` `ui` `crypto` `infra` `repo`.

Добавляйте файлы точечно, а не `git add .` — меньше шансов захватить лишнее.

### 2.4 Синхронизироваться с `master`

Раз в день, чтобы ветка не отстала:

```bash
git fetch origin
git rebase origin/master
git push --force-with-lease
```

`--force-with-lease`, а не `--force`: он не затрёт чужие коммиты, если кто-то успел запушить в вашу ветку.

Если в ветке работает кто-то ещё — вместо rebase делайте `git merge origin/master`, чтобы не переписывать историю под коллегой.

### 2.5 Открыть Pull Request

Целевая ветка — всегда `master`.

```bash
gh pr create --base master --title "fix(msg): keep attachments on forward (#174)"
```

Название совпадает с основным коммитом. Заполните шаблон, `Closes #174` обязателен — без него задача не закроется.

Переведите задачу в `In Review`.

### 2.6 Ответить на ревью

Правки — обычными коммитами в ту же ветку. Сообщение описывает изменение, а не факт правки:

```bash
git commit -m "fix(msg): handle forward without attachments (#174)"
```

`fix review` и подобное хук отклонит.

Отвечайте на каждый комментарий, даже коротко: «поправил», «оставил, потому что…». Ревьюер должен понимать, что произошло с его замечанием.

### 2.7 Merge

**Мержит автор PR после одобрения.** Ревьюер только ставит `approve` — решение о моменте merge за автором: он знает, всё ли готово, и он же на месте, если после merge что-то сломается.

Способ — **Squash and merge**. Коммиты ветки схлопываются в один, история `master` читается по задачам.

**Проверьте итоговое сообщение перед merge.** GitHub подставляет туда либо заголовок PR, либо склейку всех коммитов — второе часто выходит мусорным. Формат должен остаться прежним:

```
fix(msg): keep attachments on forward (#174)
```

После merge:

```bash
git switch master
git pull
git branch -d fix/174-forward-attachments
git fetch --prune
```

Задача закроется через `Closes`, ветка на сервере удалится.

## 3. Крупные задачи

Разбиваются на **Sub-issues**, а не на интеграционные ветки.

```text
#140 Управление групповыми чатами
├── #141 Редактирование данных группы
├── #142 Добавление участника
└── #143 Выход из группы
```

Каждая подзадача ветвится от `master` и мержится в `master` самостоятельно.

Почему не интеграционные ветки:

- они копят отставание — открытые PR отставали от `master` на 47–75 коммитов, и merge превращался в разбор конфликтов;
- удаление смерженной базовой ветки **автоматически закрывает** все направленные в неё Pull Request. Это уже происходило: три PR пришлось восстанавливать.

## 4. Перемещение и переименование файлов

Отдельным коммитом, **без правок содержимого**:

```bash
git mv старый/путь новый/путь
git commit --no-verify -m "refactor(ui): move feature components (#212)"
```

Два правила, и оба выучены на практике:

**Не смешивайте перемещение с правками.** Иначе git перестаёт видеть переименование и записывает файл как удалённый и созданный заново — история и `git blame` теряются.

**Используйте `--no-verify` для коммита-перемещения.** Prettier в pre-commit хуке форматирует staged-файлы, и этого достаточно, чтобы сломать определение переименований. В одном из коммитов так потерялась история 31 файла из 191.

Правки импортов и имён — следующим коммитом, уже с хуком.

После перемещения проверьте:

```bash
git show --summary HEAD | grep -c "^ rename"   # должно совпасть с числом файлов
```

## 5. Частые ситуации

**Закоммитил в `master` вместо ветки** (не запушено):

```bash
git branch fix/174-forward-attachments
git reset --hard origin/master
git switch fix/174-forward-attachments
```

**Забыл файл в последнем коммите** (не запушено):

```bash
git add забытый.ts
git commit --amend --no-edit
```

Если коммит уже запушен — не используйте `--amend`, сделайте новый.

**Конфликт при rebase:**

```bash
# разрешить в файле, убрать маркеры <<<<<<< ======= >>>>>>>
git add <файл>
git rebase --continue

# либо откатиться целиком:
git rebase --abort
```

**Отложить работу:**

```bash
git stash push -m "описание"
git stash pop
```

Untracked-файлы обычный stash не берёт — нужен `git stash push -u`.

**Потерял коммиты:** `git reflog`, найти SHA, `git reset --hard <sha>`. Работает примерно 90 дней.

**Откатить чужой коммит в `master`:** не переписывать историю, а сделать `git revert <sha>` в новой ветке и открыть PR.

**Хук отклонил коммит:** прочитайте сообщение. Обычно — неизвестный тип, scope не из списка, нет `(#N)`, заглавная буква или точка в конце. `--no-verify` тут не решение: та же проверка есть в CI.

**Не удаётся `git mv` каталога, `Permission denied`:** его держит запущенный процесс. Чаще всего dev-сервер Vite. Остановите его и повторите.

**После переключения веток приложение не собирается:** перезапустите dev-сервер и очистите кеш:

```bash
rm -rf frontend/node_modules/.vite
```

Vite держит в памяти граф модулей и конфигурацию — после смены структуры каталогов они устаревают.

## 6. Удаление веток

После merge ветка удаляется автоматически.

При ручной чистке недостаточно проверить, что ветка смержена. Нужно убедиться, что она не является **целевой** для открытых Pull Request:

```bash
gh pr list --state open --json headRefName,baseRefName
```

Удаление целевой ветки закрывает направленные в неё PR.

---

## 7. Чего не делать

- Не пушить в `master` напрямую.
- Не использовать `git push --force` — только `--force-with-lease` и только в своей ветке.
- Не обходить хуки через `--no-verify`, кроме коммитов-перемещений.
- Не мержить свой PR без одобрения.
- Не складывать несколько задач в одну ветку.
- Не держать ветку дольше нескольких дней.
- Не коммитить `.env`, секреты, `node_modules/`, `dist/`.
- Не переписывать историю `master` — только revert-коммиты.

## 8. Шпаргалка

```bash
# начать
git switch master && git pull
git switch -c fix/174-forward-attachments
git push -u origin fix/174-forward-attachments

# работать
git add <файлы>
git commit -m "fix(msg): keep attachments on forward (#174)"
git push

# синхронизировать
git fetch origin && git rebase origin/master
git push --force-with-lease

# PR
gh pr create --base master --title "fix(msg): ... (#174)"

# после merge
git switch master && git pull
git branch -d fix/174-forward-attachments
git fetch --prune

# посмотреть состояние
git status
git log --oneline -10
git log --oneline origin/master..HEAD    # мои коммиты сверх master
gh pr status
```

## 9. Текущее ограничение

Ветка `master` не защищена: прямой push, merge без одобрения и force-push технически возможны. Правила выше держатся на договорённости.

Включить защиту нельзя — для приватных репозиториев она доступна только на платных планах GitHub. По той же причине не работает `.github/CODEOWNERS`: ревьюеры по нему не назначаются.
