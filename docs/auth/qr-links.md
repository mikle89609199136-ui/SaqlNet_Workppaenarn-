# Контракт ссылки входа по QR (#429)

Целевой сценарий — web landing page существующего клиента, реализованная в #745.
Ссылка из QR нового устройства:

```text
https://<frontend-origin>/link#t=<qrToken>&k=<publicKey>
```

`qrToken` возвращает `POST /api/v2/auth/qr-token`. `publicKey` — созданный новым
устройством одноразовый ECDH P-256 SPKI ключ в base64url. Значения фрагмента
кодируются через URLSearchParams функцией `buildQrLink`. Origin берётся у текущего
клиента; сканер отклоняет чужой origin. `secret` из ответа API остаётся только на
новом устройстве для опроса/замены/отмены кода: в QR он не попадает.

1. Камера или сканер открывает `/link`, доступный вне AuthGuard. Фрагмент браузер
   не передаёт серверу; это страница приложения, а не `GET /auth/qr-confirm`.
2. LinkPage забирает ссылку и удаляет фрагмент из адресной строки. Если сессии нет,
   сохраняет ссылку в sessionStorage вкладки, направляет на `/login?from=%2Flink`
   и после входа возвращается к подтверждению. При запрете sessionStorage возврат
   ссылки через вход не гарантирован: понадобится повторное сканирование.
3. Вошедший клиент разбирает ссылку и вызывает `GET /api/v2/auth/qr-request/{token}`
   с session cookie. Сравнивает возвращённый ключ с ключом в QR и показывает
   запрашивающее устройство; открытие ссылки само по себе не подтверждает вход.
4. После явного подтверждения клиент отправляет `POST /api/v2/auth/qr-confirm`
   с cookie и JSON `{qrToken, payload}`. Payload содержит зашифрованную передачу
   мастер-ключа. Новое устройство получает результат через status API с secret;
   сервер устанавливает session cookie, клиент завершает вход.

Код живёт 60 секунд, обновляется через 30 секунд; после сканирования сервер
предоставляет 60 секунд на решение. Просроченный, заменённый, некорректный код или
несовпадение ключей отображаются клиентской ошибкой и не создают сессию.

Обратный сценарий, когда код показывает вошедшее устройство, уже использует
отдельные `/qr-login#t=…&k=…&s=…` и `/auth/qr-offer` API (#754); он не меняет
контракт `/link`. Старые ссылки `/api/v2/auth/qr-confirm?token=…` не генерируются
и не поддерживаются как web landing page. Нативный mobile deep link не вводится.

Реализация: shared/crypto/qrLink.ts, features/qr-login/model/useQrLogin.ts,
pages/link/ui/LinkPage.tsx, features/qr-login/ui/LinkDevicePanel.tsx и AuthService.
Описание API — backend-v2/contracts/openapi/paths/auth.yaml.
