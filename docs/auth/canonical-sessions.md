# Единая модель сессий и устройств (#706)

`auth.sessions` — источник состояния авторизации и метаданных устройства.
Каждый вход (пароль, регистрация или QR) создаёт отдельную сессию с UUID `id`
и уникальным отпечатком `access_token_hash`. Rust добавляет случайный `jti`
в каждый токен: два входа в одну секунду тоже независимы. Сырые токены в БД
не сохраняются. Смена имени устройства не меняет ID сессии.

`GET /auth/sessions` и `GET /users/devices` читают одни и те же активные
сессии, возвращают одинаковые ID и порядок. `firstLogin` в devices — это
`createdAt` сессии. `isCurrent` вычисляется по cookie конкретного запроса,
не хранится глобально. User-Agent и IP — только метаданные, не ключ поиска
сессии. `POST /users/devices/register` обновляет существующую сессию токена,
возвращая её ID; не создаёт отдельной записи и не затрагивает другие устройства.

`DELETE /users/devices/{sessionId}` отзывает выбранную сессию пользователя.
Отзыв сессии, запись отпечатка в `auth.revoked_tokens` и `pg_notify` выполняются
в одной транзакции. После commit HTTP-проверка отклоняет её токен, а все chat
реплики закрывают связанные сокеты, включая простаивающие. Проверки при
сообщениях и heartbeat покрывают пропущенное уведомление. Метаданные остальных
сессий не меняются. Чужой или неактивный ID возвращает 404, текущий — 409;
для выхода из текущей сессии используется `/auth/logout`.

`POST /users/devices/terminate-all` отзывает остальные сессии, сохраняя
сессию запроса. `/auth/logout-all` сохраняет прежнюю семантику: увеличивает
поколение токенов пользователя, отзывает все сессии, очищает cookie и push.

## Миграция и выкладка

1. Сначала выкатить Rust crypto с уникальным `jti`.
2. Остановить старые auth/user реплики: смешанная работа старой двойной записи
   с новой моделью не поддерживается. Применить `0039_canonical_device_sessions.sql`
   штатным мигратором перед запуском новых сервисов.
3. Миграция сохраняет `auth.sessions.id`, переносит метаданные только по явной
   старой связи `device_session_id` с проверкой владельца, затем удаляет связь.
   Записи без отпечатка access token помечаются отозванными. Сопоставление по
   User-Agent/IP не выполняется: оно смешало бы разные устройства.
4. Обновить все Go-сервисы, использующие общий DBTokenChecker, включая chat.
   Новые auth/user readiness-проверки требуют канонические поля метаданных.
5. Обновить открытые списки устройств на клиентах: старые legacy device UUID
   больше не являются API ID. Токены, уже имеющие запись в `auth.sessions`,
   продолжают работать; для старых токенов без такой записи нужен повторный вход.

`public.user_sessions` остаётся только замороженным legacy-снимком для
импортера. Runtime-сервисы её не читают и не записывают. Активные сессии
никогда не создаются из legacy-строк без достоверной привязки к токену.
Миграция выдерживает повторный запуск, включая прогон всей цепочки миграций
на базе без журнала `schema_migrations`.

Проверки: интеграционные тесты `internal/platform/authctx` проходят оба HTTP API
с двумя одинаковыми браузерами, стабильные ID, отзыв, logout-all и отсутствие
двойной записи; `internal/chat` проверяет закрытие сокетов выбранного устройства
на двух репликах; `cmd/migrate` — backfill и повторяемость миграции. Rust-тест
проверяет уникальность токенов последовательных входов.

## Управление в клиенте (#720)

В «Настройки → Аккаунт → Активные сеансы» текущая сессия определяется только
по `isCurrent`, независимо от порядка массива. Показываются device name/type,
`lastActive` и доступные IP/location. Некорректная дата обозначается как
«нет данных», значения Unknown скрываются. Строка без явного `isCurrent`
не получает индивидуального действия завершения.

- «Завершить» у выбранной чужой сессии подтверждает конкретное устройство и
  вызывает `DELETE /users/devices/{id}`. Текущая строка этого действия не имеет;
  пояснение направляет к отдельному выходу в разделе «Аккаунт».
- «Завершить все, кроме этого» вызывает `POST /users/devices/terminate-all` с
  отдельным подтверждением. Обе операции сохраняют текущую сессию, локальные
  E2E-ключи, черновики и остальные кеши; wipeDevice/forgetSession/logout-all
  в этих ветках не вызываются.
- Прежнее «Завершить все сеансы» сохраняет собственную семантику: включая
  текущую, с удалением локальных ключей после успешного `/auth/logout-all`.
  Оно остаётся зависимым от серверного rollout gate этого endpoint.
- Запрос отправляется только после подтверждения. До ответа строка остаётся
  в списке; повторные/конкурирующие действия и закрытие выполняющегося
  подтверждения блокируются. После успеха из кеша удаляются подтверждённые
  сессии и выполняется GET; reload страницы не нужен.
- 404 для одной сессии означает «уже завершена или недоступна», 409 объясняет
  защиту текущего сеанса; в обоих случаях список перечитывается. Ошибка записи
  не выдаёт успешного завершения. Ошибка GET после успешного revoke имеет
  отдельное сообщение и кнопку обновления без повторного DELETE. 401 использует
  общий auth cleanup/login flow с сохранением ключей на диске.
- Query/mutation разделены по owner/session epoch; отменённый/старый GET не
  устанавливает поздний список, callbacks старого владельца не обновляют новый
  кеш/подтверждение. Список перечитывается при focus/reconnect. На обзоре аккаунта
  загружается счётчик, на подстранице используется один активный query observer.

`lastActive` отображается из канонического API. Обновление активности на каждом
HTTP/WS heartbeat не добавляется этой frontend-задачей: без отдельной серверной
реализации поле может отражать вход или последнее обновление metadata.

### Проверка клиента

```sh
cd frontend
npm test
npm run api:check
npm run build
npm run check:cycles
npx playwright test -c playwright.sessions.config.ts
```

Для browser scenario нужен изолированный backend :8080 с миграциями и Vite :3000.
Четыре contexts имитируют три устройства владельца и другой аккаунт, проходят
настоящий cloud backup/unlock flow и используют реальные cookies/HTTP/WebSocket.
Проверяются выбранный UUID, HTTP 401 и закрытие сокета отозванного устройства,
сохранение доступа остальных, terminate-others, неизменность текущего public
fingerprint/черновика и переход отозванных клиентов на login через существующую
проверку сессии сокетом (#1070). Native Escape проверяется в браузере;
component tests посылают cancel event, поскольку jsdom его не генерирует.
Снимки desktop/mobile проверены визуально; UI/сеть отзыва не подменяются.

При быстром запуске четырёх клиентов с одного локального IP auth bucket стенда
должен позволять bootstrap и проверки. Использованный локальный compose override
(передать вместе с `infrastructure/docker/docker-compose.v2.yml`):

```yaml
services:
  edge:
    environment:
      EDGE_RATE_LIMIT_OTHER_AUTH_RATE: 10/s
      EDGE_RATE_LIMIT_OTHER_AUTH_BURST: 100
```

Component/integration tests покрывают подтверждение/отмену, порядок isCurrent,
selective/bulk success, 404/409/401/5xx, повторные клики, pending cancel, неудачный
refetch с повторной загрузкой, смену аккаунта и поздние ответы. Прежние проверки
logout/logout-all и удаления ключей сохранены.

Локальная приёмка 23 октября 2026: 276 файлов / 2486 Vitest tests, 28 API contract tests, production build, cycle check и lint изменённых файлов без ошибок. Browser scenario на четырёх настоящих контекстах прошёл; отдельно проверены desktop/mobile. Общий app TypeScript сохраняет те же 223 исходные ошибки проекта, новых диагностик нет; browser spec/config проходят строгую типизацию. Backend и миграции этим изменением не меняются.
