# E2E-прогон

Здесь живут пять сценариев, которые невозможно проверить в jsdom: настоящая
WebCrypto, настоящая IndexedDB, два независимых пользователя и живой сокет.

Всё остальное проверяется юнит-тестами — они на два порядка быстрее и не
зависят от доступности стенда. Если сценарий можно написать в `src/**/*.test.ts`,
он должен быть написан там.

## Запуск

Нужен доступ к стенду. Проверьте, что в `frontend/.env` задан прокси:

```
DEV_API_PROXY_TARGET=https://craneapp-timkhazatsky.amvera.io
```

Прямые запросы с `localhost` стенд отклоняет по CORS, поэтому тесты идут
через dev-сервер Vite — он поднимается автоматически.

```bash
cd frontend
npm run e2e              # весь прогон
npm run e2e:ui           # интерактивный режим, удобно для разбора падений
npx playwright test e2e/crypto-roundtrip.spec.ts   # один файл
npx playwright show-report                          # отчёт после прогона
```

Первый запуск скачает браузер: `npx playwright install chromium`.

## Учётные записи

Тесты работают под двумя заранее заведёнными пользователями стенда. Их имена
и пароль берутся из переменных окружения:

```
E2E_USER_A=e2e_alice_test
E2E_USER_B=e2e_boris_test
E2E_PASSWORD=…
```

Значения по умолчанию заданы в `e2e/fixtures/accounts.ts`. Пароль в
репозиторий не коммитится.

## Почему логин идёт через API

`storageState` Playwright сохраняет cookies и localStorage, но **не сохраняет
IndexedDB** — а именно там лежат ключи шифрования. Восстановленная из
`storageState` сессия выглядит рабочей ровно до первой попытки расшифровать
сообщение.

Поэтому установка сессии выглядит так: логин запросом к API, полученная cookie
и профиль ставятся в новый браузерный контекст до открытия страницы — и ключи
создаются в самом браузере теми же путями, что у настоящего пользователя.
Каждый контекст проходит это самостоятельно: два пользователя обязаны иметь
разные ключи, иначе тест на шифрование ничего не проверяет.

## Прогон пишет в общий стенд

Тесты отправляют настоящие сообщения настоящим пользователям и создают
настоящие группы. Отсюда два следствия:

1. `workers: 1` — параллельный прогон означал бы, что один сценарий видит
   сообщения другого в списке чатов;
2. каждый сценарий помечает свои сообщения уникальной меткой и ищет в DOM
   именно её, а не «последнее сообщение».

## Когда падает

Сначала посмотрите отчёт: `npx playwright show-report`. К упавшему сценарию
приложены запись экрана и трасса — по ней видно, на каком шаге и что было на
странице.

Частые причины, не связанные с кодом:

- стенд не отвечает или отвечает медленнее обычного;
- тестовая учётная запись потеряла ключи (например, после входа с другого
  устройства) — тогда старые сообщения показывают плейсхолдер, и это
  ожидаемое поведение продукта, а не дефект;
- в списке чатов накопились сообщения от прошлых прогонов.
